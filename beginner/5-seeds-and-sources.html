Seeds & Sources Explained

Load small reference CSVs with seeds and register raw warehouse tables with sources.

Every dbt project starts from data it did not create. There are two neat ways to bring that data in: seeds for small CSVs you version-control, and sources for raw tables your EL tool already loaded into the warehouse. This lesson covers both — and how to check whether your sources are fresh.

Two doors into the project

A seed is a file you own that dbt loads. A source is a table someone else owns that dbt only reads. Once inside, both behave like normal data your models can query.

Two ways in #

country_codes.csv dbt seed → table your models

Seeds — small CSVs under version control #

A seed is a static CSV in the seeds/ folder. dbt loads it into the warehouse as a table, so the data is reviewable in the same pull request as the model that uses it. Keep seeds small — they are for reference data, not exports.

Create the CSV #

seeds/country_codes.csv csv 
code,country_name,region
US,United States,North America
CA,Canada,North America
GB,United Kingdom,Europe
DE,Germany,Europe
JP,Japan,Asia-Pacific

Load it #

terminal bash 
dbt seed                         # loads every seed
dbt seed --select country_codes  # loads only this one

Verify it #

terminal bash 
duckdb ecommerce.duckdb
select * from main.country_codes;

You can pin column types when the CSV is ambiguous — for example so a code stays a string rather than becoming a number:

dbt_project.yml yaml 
seeds:
  ecommerce_analytics:
    country_codes:
      +column_types:
        code: varchar          # force "US" to stay text
        country_name: varchar

Sources — raw tables you only observe #

A source is a table dbt does not create. Declare it once in a _sources.yml file so dbt knows where it lives, then read it with {{ source('group', 'table') }}. dbt records the edge in the lineage graph and can test and freshness-check it.

models/_sources.yml yaml 
version: 2

sources:
  - name: ecommerce
    description: "Raw e-commerce tables landed by the EL job."
    schema: main
    loaded_at_field: _loaded_at      # timestamp used for freshness
    freshness:
      warn_after:  {count: 12, period: hour}
      error_after: {count: 24, period: hour}
    tables:
      - name: orders
        description: "One row per order line."
        columns:
          - name: order_id
            description: "Order identifier"
          - name: customer_id
            description: "FK to customers"

Check source freshness #

Freshness compares the newest value in loaded_at_field against the thresholds you set, so a stalled pipeline becomes a warning or an error instead of a silent one.

terminal bash 
dbt source freshness
OutcomeMeaning
passThe newest row is within warn_after
warnData is older than warn_after but within error_after
errorData is older than error_after — the pipeline is likely broken

Use a seed and a source in one model #

The seed is reached with ref(), the raw table with source(). Mixing them up is the single most common beginner mistake.

models/orders_by_region.sql sql 
select
    cc.region,
    count(*)                     as total_orders,
    sum(o.line_total)            as revenue
from {{ ref('first_orders') }} as o
left join {{ source('ecommerce', 'customers') }} as cust
    on o.customer_id = cust.id
left join {{ ref('country_codes') }} as cc
    on cust.country_code = cc.code
group by cc.region
order by revenue desc
Do not join on a bare table name

Joining on a bare table name such as join customers c bypasses dbt entirely. Use {{ ref('country_codes') }} for the seed and {{ source('ecommerce', 'customers') }} for the raw table so the dependency graph stays correct.

Seeds vs sources: which one? #

Question Seed Source
Where does the data live before dbt?A CSV in your repoA table in the warehouse
Who creates the warehouse table?dbt, with dbt seedYour EL tool
How do you reference it?{{ ref('name') }}{{ source('group', 'table') }}
Best forLookups, mapping tables, test fixturesBusiness data landed from upstream systems
Keeps history in Git?Yes — every rowNo — only the declaration

See the lineage #

Because every source and seed is declared, dbt can draw the full path from a raw table to the dashboard that consumes it. dbt docs generate builds the documentation site, and dbt docs serve opens the interactive lineage graph.

terminal bash 
dbt docs generate   # build the docs + lineage catalog
dbt docs serve      # open it in your browser

Key takeaways #

  • Seeds are small CSVs dbt loads with dbt seed; reference them with {{ ref('name') }}.
  • Sources are raw warehouse tables declared in _sources.yml; read them with {{ source('group', 'table') }}.
  • Add loaded_at_field and freshness thresholds, then run dbt source freshness to detect stale data.
  • Never join on a bare table name — always go through ref() or source().
  • Declaring both makes dbt docs show end-to-end lineage from raw table to dashboard.
