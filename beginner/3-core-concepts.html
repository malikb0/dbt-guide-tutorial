Core Concepts: Models, Sources & Seeds

The four building blocks of every dbt project — and how ref() stitches them into a DAG.

dbt has a deliberately small vocabulary. Four words — model, source, seed and test — describe almost everything you will ever do. Learn what each one is and the rest of dbt is just detail.

The whole pipeline in one line

Sources (raw tables) and seeds (committed CSVs) feed models, models produce the tables your BI tool reads, and tests stand guard at every step. That is the entire architecture.

The four building blocks #

Model

A .sql file with one SELECT. dbt compiles it and creates a table or view. This is where most of your work happens.

Source

A raw upstream table dbt does not manage. You declare it once so dbt can track lineage and freshness.

Seed

A small CSV file committed to the repository. dbt loads it into the warehouse as a table.

Test

An assertion about your data, such as “this column is never null”. dbt fails the build when data breaks the rule.

Models — the transformations you write #

A model is one .sql file containing a single SELECT. You do not write CREATE TABLE; dbt wraps your query in the right DDL, in the right schema, in the right order.

models/first_orders.sql sql 
-- One model = one SELECT. dbt provides the CREATE.
select
    o.order_id,
    o.customer_id,
    o.product_sku,
    o.quantity,
    o.unit_price,
    o.quantity * o.unit_price as line_total,
    cast(o.order_date as date) as order_day
from {{ source('ecommerce', 'orders') }} as o
where o.status = 'completed'
Never hard-code a table name

Always reference another model as {{ ref('my_model') }}. Writing from my_model works by accident on your machine but hides the dependency from dbt — so it will not rebuild downstream models or draw the edge in the lineage graph.

Sources — raw tables dbt only observes #

Sources are the tables an extract-and-load tool already put in your warehouse. You never transform them in place; you declare them in a YAML file and read them with {{ source(...) }}.

models/_sources.yml yaml 
version: 2

sources:
  - name: ecommerce            # the group you name in source()
    schema: main               # where the raw tables live
    tables:
      - name: orders
        description: "One row per order line, loaded by the EL job."
        columns:
          - name: order_id
            description: "Order identifier"
          - name: customer_id
            description: "FK to the customers table"

Then in a model: select * from {{ source('ecommerce', 'orders') }}. dbt records the dependency, can test the source, and can check how fresh it is.

Seeds — small CSVs under version control #

A seed is the one place where dbt accepts something other than SQL. It is a CSV checked into the repo and loaded with dbt seed — ideal for lookup tables like country codes or pricing tiers.

seeds/country_codes.csv csv 
code,country_name,region
US,United States,North America
CA,Canada,North America
GB,United Kingdom,Europe
DE,Germany,Europe
JP,Japan,Asia-Pacific
terminal bash 
dbt seed                       # load every seed
dbt seed --select country_codes  # load just one
A seed is referenced with ref()

Because dbt loads a seed itself, you read it with {{ ref('country_codes') }}, not {{ source(...) }}. Sources are for tables dbt does not create; seeds are for tables it does.

Tests — assertions about your data #

A test states a rule that must always hold. Generic tests are declared in YAML next to the model; dbt compiles each into a query that returns the rows breaking the rule. Zero rows means the test passes.

Generic testThe rule it checks
not_nullThe column contains no nulls
uniqueEvery value in the column appears exactly once
accepted_valuesEvery value belongs to an allowed list
relationshipsEvery value exists in another model's column (a foreign key)

We cover tests fully in Basic Tests.

ref() and source() build the DAG #

Every ref() and source() call is an edge in a Directed Acyclic Graph. dbt reads those edges and works out the build order for you — you never schedule models by hand.

ecommerce.orders first_orders order_summary
1
Parse

dbt finds every ref() and source() and builds the graph.

2
Compile

Jinja is rendered and references are swapped for real table names.

3
Execute

dbt walks the graph top to bottom and runs each model.

Layering a project: staging, intermediate, marts #

Real projects do not build one giant query. They stack small models into layers, each with a clear job. This keeps logic reusable and makes the lineage readable.

LayerNamingIts job
Stagingstg_ordersOne staging model per source: rename, cast, standardise. No joins.
Intermediateint_orders_joinedReusable joins and business logic that more than one mart needs.
Martsfct_orders, dim_customersBusiness-ready tables that BI tools and dashboards query.

Key takeaways #

  • Models are SQL transformations; sources are raw tables dbt only observes; seeds are committed CSVs; tests are assertions.
  • Reference models with {{ ref('name') }} and raw tables with {{ source('group', 'table') }} — never a bare table name.
  • A seed is read with ref() because dbt creates it; a source is read with source() because dbt does not.
  • ref() and source() turn loose queries into a dependency graph dbt executes in order.
  • Layer projects as staging → intermediate → marts so logic stays reusable and readable.
