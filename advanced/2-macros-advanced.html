Advanced Macro Patterns

Dispatch, adapter-aware SQL, run_query and packaging macros into installable dbt packages.

Your progress

A macro is a function for SQL: write the logic once, call it from any model. You met simple macros at the intermediate level. Here we go deeper — adapter-aware SQL with adapter.dispatch, querying the warehouse from Jinja with run_query and the execute guard, and shipping macros to your whole team as a dbt package.

Macros generate SQL — they do not move data

A macro is a reusable Jinja template. When dbt compiles a model, every macro call is replaced with the SQL text it returns before that statement reaches your warehouse.

From copy-paste to one definition #

Suppose three staging models all convert a cents column into dollars. Copying the same round(... / 100.0, 2) into every file is exactly how small inconsistencies become big reconciliation problems. A macro keeps a single definition.

macros/cents_to_dollars.sql sql 
{% macro cents_to_dollars(column_name, scale=2) %}
    round({{ column_name }} / 100.0, {{ scale }})
{% endmacro %}

Call it like a function. dbt resolves the arguments while compiling the model, so the warehouse only ever sees plain SQL:

models/stg_payments.sql sql 
select
    payment_id,
    {{ cents_to_dollars('amount_cents') }} as amount,
    payment_method
from {{ source('ecommerce', 'payments') }}

Macros live in macros/*.sql and are visible everywhere in the project. Because they render at compile time, a macro can generate whole column lists, joins or CASE expressions — not just scalar helpers.

Making macros adapter-aware with adapter.dispatch #

Every warehouse speaks slightly different SQL. A team that runs dbt on DuckDB in development and BigQuery in production cannot hard-code date_trunc and hope it behaves the same. Multiple dispatch solves this: you call one macro name, and dbt picks the implementation that matches the active adapter.

The dispatch pattern #

Three parts: a thin primary macro that dispatches, a default__ implementation that works anywhere, and adapter-specific overrides named <adapter>__.

macros/month_start.sql sql 
{% macro month_start(date_column) %}
    {{ return(adapter.dispatch('month_start', 'my_shop')(date_column)) }}
{% endmacro %}

{% macro default__month_start(date_column) %}
    date_trunc('month', {{ date_column }})
{% endmacro %}

{% macro bigquery__month_start(date_column) %}
    timestamp_trunc({{ date_column }}, month)
{% endmacro %}
How the search resolves

For each call, dbt looks for bigquery__month_start first, then default__month_start. The macro_namespace argument ('my_shop') scopes the search to your project; packages pass their own package name so they can be extended or overridden safely.

Call the macro by its primary name; the caller never knows which SQL it got:

models/monthly_revenue.sql sql 
select
    {{ month_start('order_date') }} as month,
    sum(quantity * unit_price) as revenue
from {{ ref('stg_orders') }}
group by 1

Running SQL from Jinja: run_query and the execute guard #

Most macros only render text. Sometimes you need a real answer from the warehouse while compiling — the list of distinct payment methods, the newest order date, whether a table exists. That is what run_query is for.

models/payment_methods_pivot.sql sql 
{% set query %}
    select distinct payment_method
    from {{ ref('stg_payments') }}
    order by 1
{% endset %}

{% set results = run_query(query) %}

{% if execute %}
    {% set methods = results.columns[0].values() %}
{% else %}
    {% set methods = [] %}
{% endif %}

select
    order_id,
    {% for method in methods %}
    sum(case when payment_method = '{{ method }}' then amount end) as {{ method }}_amount,
    {% endfor %}
    sum(amount) as total_amount
from {{ ref('stg_payments') }}
group by 1
Always guard database reads with {% if execute %}

dbt parses every file before it runs anything. During that parse, execute is False and no query has returned a table, so touching results.columns raises 'None' has no attribute 'table'. Wrapping the access in {% if execute %} keeps parsing clean.

execute vs run: what fires when #

Keep the two phases separate in your head:

PhaseexecuteWhat happens
ParsingFalsedbt reads files, finds ref()/source(), builds the DAG. No SQL runs.
Compilation with a connectionTrueJinja is rendered fully; run_query calls actually hit the warehouse.
ExecutionTrueMaterializations create or update the tables — this is the model's own SQL running.

One subtlety: execute is also True when dbt compiles with a live connection, including dbt compile and dbt docs generate. If a macro has side effects (an INSERT, DELETE or VACUUM), scope it to the commands you mean with flags.WHICH:

macros/record_run.sql sql 
{% macro record_run(model_name) %}
    {% if execute and flags.WHICH in ['run', 'build'] %}
        {% call statement('audit', fetch_result=False) %}
            insert into audit_log (model_name, ran_at)
            values ('{{ model_name }}', current_timestamp)
        {% endcall %}
    {% endif %}
{% endmacro %}

Use run_query when you want results back. Use a statement block with fetch_result=False for fire-and-forget DDL/DML, because run_query returns none for statements that produce no result set.

Shipping macros with dbt packages #

A dbt package is a git or hub-installed project whose macros become available to yours. They are installed by adding to packages.yml and running dbt deps.

packages.yml yaml 
packages:
  - package: dbt-labs/dbt_utils
    version: [">=1.1.0", "<2.0.0"]
  - package: calogica/dbt_expectations
    version: [">=0.10.0", "<0.11.0"]
Try itterminal
terminal bash 
dbt deps

dbt downloads each package into dbt_packages/ and registers its macros. Commit packages.yml and package-lock.yml, not the downloaded folder.

Now call the package's macros with dot notation. This one builds a stable surrogate key from several columns:

models/fct_order_lines.sql sql 
select
    {{ dbt_utils.generate_surrogate_key(['order_id', 'order_line_id']) }} as order_line_sk,
    order_id,
    product_id,
    quantity * unit_price as line_total
from {{ ref('stg_order_lines') }}

Macro namespacing and safe overrides #

Macros share one global namespace, so a careless name can collide with a package. dbt's convention is simple: use a descriptive prefix, and reference package macros with package.macro.

Where the macro livesHow you call itExample
Your projectBare name{{ cents_to_dollars('amount_cents') }}
Installed packagePackage dot macro{{ dbt_utils.generate_surrogate_key([...]) }}
Adapter-awarePrimary dispatch name{{ month_start('order_date') }}
Your overrideSame default__ namedefault__generate_surrogate_key

To change how a package's internal macros behave, add a project-level dispatch config and put your project ahead of the package. Then define the override with the conventional default__ name.

dbt_project.yml yaml 
dispatch:
  - macro_namespace: dbt_utils
    search_order: ['my_shop', 'dbt_utils']
macros/override_surrogate_key.sql sql 
{% macro default__generate_surrogate_key(field_list) %}
    {{ return(my_shop_hash(field_list)) }}
{% endmacro %}
Do not override built-in context properties

ref, source and config cannot be overridden through dispatch — they are dbt context properties, not dispatched macros. If you need a custom generate_schema_name, override that by name or register a default__ candidate in a package.

Pitfalls to avoid #

Calling run_query without an execute guard

Parsing happens for every command, so the query has not run and the result is none. Guard the result access with {% if execute %}.

Side effects firing during dbt docs generate

execute is true whenever dbt compiles with a connection. Add flags.WHICH in ['run', 'build'] before any DML.

Shadowing a package macro by accident

Prefix your macros (my_shop_) and call package macros through their namespace so there is never ambiguity.

Over-macroing

A macro that hides a single simple expression makes the model harder to read. Reach for a macro when the logic repeats or genuinely varies by adapter.

Key takeaways #

  • Macros render SQL at compile time; they are functions for Jinja, not stored procedures.
  • adapter.dispatch lets one macro call resolve to adapter-specific SQL, with a default__ fallback.
  • run_query fetches warehouse results during compilation; guard result access with {% if execute %}.
  • Scope side-effecting SQL to specific commands with flags.WHICH so docs builds stay read-only.
  • Packages are installed via packages.yml and dbt deps; call their macros with package.macro.
  • Namespace your macros and override package behavior with a dispatch search_order plus a default__ macro.
