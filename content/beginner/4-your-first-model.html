Time to ship something. In this lesson you will write a model, compile it to see the real SQL dbt generates, run it against DuckDB, inspect the resulting table, and add your first test. Every command is real and every file is one you can keep.

{{icon:target}}
The goal

Build first_orders — a clean order table that joins raw orders to raw customers, keeps only completed orders, and computes a line total. Then prove it works with a test.

What you are building

The model reads two sources and produces one table. dbt figures out that it must read the sources before it can build the model — that ordering is the DAG.

Step 1 — Check your setup

From inside the project directory, confirm dbt can reach DuckDB before you write anything.

{{icon:terminal}} Try itterminal
terminal bash 
cd ~/projects/ecommerce_analytics
dbt debug

Expected: All checks passed! If not, revisit Setup & Installation.

Step 2 — Write the model

Create a file at models/first_orders.sql. It contains exactly one SELECT, nothing else.

models/first_orders.sql sql 
-- Join raw orders to raw customers and keep only completed orders.
select
    o.order_id,
    o.customer_id,
    c.name                                as customer_name,
    o.product_sku,
    o.quantity,
    o.unit_price,
    o.quantity * o.unit_price             as line_total,
    cast(o.order_date as date)            as order_day
from {{ source('ecommerce', 'orders') }} as o
left join {{ source('ecommerce', 'customers') }} as c
    on o.customer_id = c.id
where o.status = 'completed'

Three things are worth noticing:

  • {{ source('ecommerce', 'orders') }} tells dbt which declared source table to read.
  • Aliases keep the join readable, and the calculation lives in the model rather than in a dashboard.
  • There is no CREATE statement — dbt writes that part for you.

Step 3 — Compile before you run

dbt compile renders the Jinja and resolves every reference, but touches no data. It is the fastest way to see what dbt will actually execute.

terminal bash 
dbt compile

# The rendered SQL lands under target/
cat target/compiled/ecommerce_analytics/models/first_orders.sql

With source('ecommerce', 'orders') resolved, the compiled file looks like this (the catalog prefix comes from your DuckDB file name):

target/compiled/…/first_orders.sql sql 
select
    o.order_id,
    o.customer_id,
    c.name                     as customer_name,
    o.product_sku,
    o.quantity,
    o.unit_price,
    o.quantity * o.unit_price  as line_total,
    cast(o.order_date as date) as order_day
from "ecommerce"."main"."orders" as o
left join "ecommerce"."main"."customers" as c
    on o.customer_id = c.id
where o.status = 'completed'
{{icon:search}}
Compile is your debugger

When a model errors, open its compiled file first. Nine times out of ten the problem is a Jinja reference that resolved to something other than what you expected.

Step 4 — Run the model

Now let dbt execute the compiled SQL against DuckDB. --select limits the run to one model while you iterate.

terminal bash 
# Build just this model
dbt run --select first_orders

Expected output ends with a summary such as Completed successfully and Done. PASS=1 WARN=0 ERROR=0. The first run also creates the ecommerce.duckdb file and the main schema.

Step 6 — Make it a physical table

New models default to a view. Add a config() block at the top of the file to store first_orders as a table instead. This is how you control each model's materialization.

models/first_orders.sql sql 
{{ config(materialized='table') }}

select
    o.order_id,
    -- … the rest of the query from step 2 …
from {{ source('ecommerce', 'orders') }} as o
{{icon:triangle-alert}}
The key is materialized

A common mistake is writing materialization='table'. dbt silently ignores unknown config keys, so the model quietly stays a view. The correct key is materialized='table' — the same word you use in dbt_project.yml as +materialized.

Step 7 — Add your first test

A table without tests is a rumour. Declare two generic tests on order_id in a YAML file next to the model, then run dbt test. Tests pass when they return zero rows.

{{diagram:tests|Tests sit between a model and its consumers: if a rule breaks, the build stops before bad data spreads.}}
models/_models.yml yaml 
version: 2

models:
  - name: first_orders
    description: "Completed orders with customer details and a line total."
    columns:
      - name: order_id
        description: "Unique identifier for each order"
        tests:
          - not_null
          - unique
terminal bash 
dbt test --select first_orders

Expected: two passing tests and a summary ending PASS=2 WARN=0 ERROR=0. From now on, dbt build --select first_orders runs the model and its tests together, in order.

Key takeaways

  • {{icon:circle-check}}A model is one SELECT; dbt generates the CREATE statement.
  • {{icon:circle-check}}dbt compile renders Jinja and resolves references without touching data — use it to debug.
  • {{icon:circle-check}}dbt run --select first_orders executes the model; output lands in the main schema of your DuckDB file.
  • {{icon:circle-check}}{{ config(materialized='table') }} controls whether a model is a view or a table.
  • {{icon:circle-check}}Declare not_null and unique in _models.yml and run them with dbt test.
