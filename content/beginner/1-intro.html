Before dbt, analytics SQL lived in a strange place: queries pasted into BI tools, stored procedures nobody dared touch, and the same transformation copied into a dozen dashboards. dbt gave that SQL an engineering workflow — version control, tests, documentation and a dependency graph. This lesson is the map of the whole course.

{{icon:lightbulb}}
The one-sentence definition

dbt is a SQL compiler and workflow tool: you write SELECT statements as files, and dbt turns them into tables and views in your warehouse — in the right order, tested, and documented.

The problem dbt solves

Data teams used to transform data with a pile of disconnected habits. Each one felt fine in isolation, and together they made the warehouse impossible to trust.

SQL scattered everywhere

What dbt actually is

You write models — plain .sql files, each containing one SELECT. dbt compiles those files, resolves the references between them, and runs the results against your warehouse.

{{diagram:pipeline|dbt sits between your raw tables and your dashboards, turning SQL files into a governed transformation layer.}}

Four verbs describe everything dbt does

  1. Organize SQL into modular, version-controlled models.
  2. Transform raw data into business-ready layers.
  3. Test every step automatically and fail early.
  4. Document lineage so anyone can trace a number home.

A model, in full

This is a complete dbt model. It reads a source table, renames a couple of columns, computes a line total, and keeps only completed orders.

models/first_orders.sql sql 
-- One model = one SELECT. dbt handles the CREATE.
select
    order_id,
    customer_id,
    product_sku,
    quantity,
    unit_price * quantity as line_total,
    order_date,
    cast(status as text) as order_status
from {{ source('ecommerce', 'orders') }}
where status = 'completed'

Two things make this more than a saved query:

{{icon:search}}
{{icon:braces}} source() declares where raw data lives

{{ source(...) }} points at a table dbt doesn't own. dbt records the dependency, can check the source's freshness, and shows it in the lineage graph.

{{icon:git-branch}}
{{icon:git-branch}} ref() builds the dependency graph

{{ ref(...) }} points at another model. dbt uses it to work out build order and to know what to rebuild when something changes.

Models reference each other: the DAG

When one model references another, dbt assembles a Directed Acyclic Graph (DAG) and runs the nodes in dependency order. You never schedule them by hand.

{{diagram:first-model|first_orders() depends on the source, and order_summary() depends on first_orders().}}
1
Parse

dbt reads every model and macro, and finds all ref() and source() calls.

2
Compile

Jinja is rendered and the references are swapped for real table names, producing pure SQL.

3
Execute

dbt walks the DAG top to bottom and runs each model against your warehouse.

Where dbt fits in the stack

dbt does the T in ELT — after data has been extracted and loaded. It does not move data between systems; it transforms data already sitting in your warehouse.

StageWhat happensTypical tools
Extract & loadData is pulled from source systems into the warehouseAirbyte, Fivetran, custom scripts
{{icon:git-branch}} TransformRaw tables are cleaned, joined and aggregated into martsdbt
AnalyzeBI tools query the martsMetabase, Looker, Tableau
{{icon:triangle-alert}}
dbt is not an orchestrator

dbt runs the transformations you ask it to. Scheduling “run dbt every morning at 6am” is a job for Airflow, Dagster, Prefect or a cron job — dbt just executes the models.
