A dashboard built on untested data is a confident lie. dbt makes testing part of the normal workflow: declare a rule next to a column, run dbt test, and the build fails the moment the data stops obeying it. This lesson covers the four built-in generic tests and how to read a failure.

{{icon:shield-check}}
Tests are assertions, not dashboards

Each test compiles to a query that returns the rows which break the rule. No rows returned means the test passes. That is the whole idea — and it is why a test can fail loudly without any extra tooling.

Where tests attach

A test attaches to a model and, usually, to one of its columns. You declare it in YAML beside the model, so the rule lives in version control with the code it protects.

{{diagram:first-model|The model we built in the previous lesson — first_orders() — is exactly the kind of node you guard with tests.}}

The four generic tests

dbt ships four generic tests out of the box. Most data-quality rules you need at the start are combinations of these.

{{diagram:tests|Only passing data moves on to the mart; a failing test stops the build before the bad rows spread.}}
TestRuleTypical use
not_nullThe column has no nullsPrimary keys and required fields
uniqueEach value appears oncePrimary keys, emails, SKUs
accepted_valuesEvery value is in an allowed listStatus and category columns
relationshipsEvery value exists in another model's columnForeign keys, referential integrity
{{icon:info}}
Advanced tests come from packages

Anything beyond these four — like unique_combination_of_columns — comes from the dbt_utils package. Add it to packages.yml and run dbt deps to install it. We cover that in the intermediate track.

Add tests in YAML

Declare tests under each column in a _models.yml file. The example below uses all four built-ins.

models/_models.yml yaml 
version: 2

models:
  - name: first_orders
    description: "Completed orders with customer details and a line total."
    columns:
      - name: order_id
        description: "Unique order identifier"
        tests:
          - not_null
          - unique
          - relationships:
              to: source('ecommerce', 'orders')
              field: order_id

      - name: customer_id
        description: "FK to the customers table"
        tests:
          - not_null

      - name: order_status
        description: "Order lifecycle status"
        tests:
          - accepted_values:
              values: ['completed', 'pending', 'returned']

Run the tests

dbt test runs every test in the project. Use --select to narrow the run while you iterate.

terminal bash 
dbt test                              # every test
dbt test --select first_orders        # only this model's tests
dbt test --select source:ecommerce    # tests declared on sources
{{icon:terminal}} Try itterminal
terminal bash 
dbt test --select first_orders

Expected: a line per test, each marked PASS, ending with Done. PASS=5 WARN=0 ERROR=0 SKIP=0. A FAIL means the test found rows that break the rule.

What dbt runs under the hood

Generic tests are just macros that emit SQL. Knowing the shape of that SQL makes failures easy to interpret.

generated test SQL sql 
-- not_null(order_id): any row here is a failure
select *
from "ecommerce"."main"."first_orders"
where order_id is null

-- unique(order_id): any row here is a failure
select
    order_id,
    count(*) as n_records
from "ecommerce"."main"."first_orders"
group by order_id
having count(*) > 1
{{icon:search}}
The old page had these backwards

not_null does not group and count; it simply selects rows where the column is null. unique is the one that groups and uses having count(*) > 1. Reading the compiled query in target/compiled/ shows exactly which rule fired.

Read a failure and fix it

Suppose two orders share the same order_id. The unique test returns those two rows, so dbt reports a failure and names the test.

TestModelColumnResultWhat it means
not_nullfirst_ordersorder_idPASSNo null identifiers
uniquefirst_ordersorder_idFAIL2 rows share an order_id
accepted_valuesfirst_ordersorder_statusPASSOnly allowed statuses present
relationshipsfirst_ordersorder_idPASSEvery key exists upstream
1
Read the failing query

dbt prints how many rows it found. Open the compiled test in target/compiled/ to see the exact rule.

2
See the offending rows

Run dbt test --select first_orders --store-failures. dbt writes the failing rows to a table so you can query them directly.

3
Fix the model, not the test

Add a deduplication or filter to the model, re-run dbt build, and confirm the test now passes. Only weaken a test if the business rule genuinely changed.

{{icon:triangle-alert}}
Do not silence a test to make the build green

A failing test is information. Deleting it hides the problem and erodes trust in every other test. Fix the data or deliberately update the assertion — and say why in the pull request.

run, test or build?

CommandWhat it does
dbt runBuilds models only — no tests, no seeds
dbt testRuns tests only, against whatever is already built
dbt seedLoads CSV seeds only
dbt buildRuns seeds, models, snapshots and tests together, in DAG order

dbt build is the command to reach for in production and CI: it interleaves each model with its tests, so a broken model fails before its downstream dependencies ever run.

Key takeaways

  • {{icon:circle-check}}dbt ships four generic tests: not_null, unique, accepted_values and relationships.
  • {{icon:circle-check}}Declare tests under each column in _models.yml; they live in Git with the model.
  • {{icon:circle-check}}A test passes when its query returns zero rows; any returned row is a failure.
  • {{icon:circle-check}}dbt test --store-failures writes the offending rows to a table so you can inspect them.
  • {{icon:circle-check}}dbt build runs seeds, models, snapshots and tests in DAG order — the safest default.
