A dbt project only earns its keep when someone runs it on every change. CI/CD is the automation layer around your models: continuous integration verifies each pull request before it merges, and continuous delivery ships the result to production. This page is the conceptual map — the advanced level walks through a complete GitHub Actions workflow.

{{icon:lightbulb}}
Two ideas, one pipeline

Continuous integration (CI) runs on a branch or pull request: compile the project, build and test it somewhere safe, and block the merge if anything fails. Continuous delivery/deployment (CD) runs after the merge: build the artifact and promote it to the environments it belongs in.

Why automate a dbt pipeline

Running dbt build by hand works until two people change the same model, a source column is renamed, or a test starts failing silently. CI/CD replaces “did you remember to run it?” with a guarantee.

{{icon:git-pull-request}}
Catch breakage early

Every pull request compiles and tests, so a broken ref() or failed test never reaches main.

{{icon:package}}
Repeatable environments

The runner installs the same Python, adapter and packages every time — no “works on my machine”.

{{icon:flask-conical}}
Tests gate the merge

Data quality becomes a merge requirement instead of an afterthought noticed by a stakeholder.

{{icon:rocket}}
Predictable deploys

The same build that passed CI is the one promoted to production — no manual re-runs.

{{icon:triangle-alert}}
dbt Core is not a scheduler

dbt executes the commands you give it and then exits. “Run every morning at 06:00” is the job of GitHub Actions schedules, cron, Airflow, Dagster or dbt Cloud jobs — not dbt itself.

They are often spoken of as one word, but they answer different questions and run at different moments.

What runs, and when

Most teams follow the same rhythm. The triggers differ, but the sequence is stable.

On pull request
Compile, build and test in a preview schema

Install dependencies with dbt deps, then run dbt build against a CI target that writes to a disposable schema. Any failed test blocks the merge.

On merge to main
Build the deployable artifact

The same project is built again, producing manifest.json and run_results.json in target/. Those artifacts describe exactly what was compiled and run.

On release
Promote to staging, then production

CD applies the built project to each environment with the matching target. Promotion should reuse the same artifact rather than rebuild from scratch.

On a schedule
Refresh on a timer

A cron or Actions schedule runs the daily build so dashboards reflect new data even with no code change.

Where CI/CD settings live

dbt project settings are plain files, so a CI system mostly needs to install dbt, point it at a profile, and call the right commands.

{{icon:git-branch}}Commit {{icon:arrow-right}} {{icon:workflow}}Workflow file {{icon:arrow-right}} {{icon:key}}Profile + secrets {{icon:arrow-right}} {{icon:terminal}}dbt build

GitHub Actions is the most common choice for dbt projects. A workflow is a YAML file in .github/workflows/; an event like pull_request triggers it; and a job runs on a fresh virtual machine called a runner.

You bring the runner. A service such as GitHub Actions checks out the repo, installs dbt and calls dbt build. Scheduling and secrets are yours to manage in the workflow file.

The scheduler is built in. dbt Cloud runs jobs on managed infrastructure, with environments, job schedules and CI checks configured in its UI or API instead of a runner you maintain.

A minimal CI workflow

This intro-level workflow builds and tests every pull request against a separate target. The advanced level adds linting, artifact reuse and pull-request comments.

.github/workflows/dbt.yml yaml 
name: dbt CI

on:
  pull_request:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    env:
      DBT_PROFILES_DIR: .
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: pip install "dbt-duckdb>=1.8"
      - run: dbt deps
      - run: dbt build --target ci
{{icon:key}}
Secrets never belong in the repo

Commit connection details that are not sensitive, and inject credentials at run time through the CI system’s secret store (for example env: values backed by repository secrets). A committed profiles.yml with a password is a leak.

Keep CI away from production

The single most important safety rule is that a pull request must never write to your production schema. Give the CI run its own target and let it write to a disposable schema that is dropped or overwritten freely.

Targets isolate environments

A profile can hold several targets — dev, ci, prod — that differ only in schema or database. Selecting one is a flag:

terminalbash
dbt build --target ci

CI writes to the ci schema, so a failed experiment can never corrupt the tables your dashboards read.

Common pitfalls

Running CI against production data

A pull request that writes into the production schema can overwrite live tables with half-finished logic. Always isolate CI into its own target and schema.

Forgetting dbt deps

Packages declared in packages.yml are not committed. A clean runner has no dbt_packages/ until it runs dbt deps, so macros from packages look missing.

Only running models, never tests

dbt run builds models but does not run tests. Use dbt build, which runs and tests nodes in DAG order, so a failing test stops the bad data from flowing downstream.

Deploying a rebuild instead of the verified build

If CD rebuilds from a different commit than the one CI approved, you have not actually verified what shipped. Promote the artifact CI produced — the manifest.json records what was built.

Key takeaways

  • {{icon:circle-check}}CI verifies each change in an isolated target; CD promotes the verified result to the environments it serves.
  • {{icon:circle-check}}dbt Core runs commands and exits — a scheduler (Actions, cron, an orchestrator) decides when they run.
  • {{icon:circle-check}}dbt build runs models, tests, snapshots and seeds in DAG order; it is the natural CI command.
  • {{icon:circle-check}}Use targets and separate schemas so a pull request can never touch production.
  • {{icon:circle-check}}Keep credentials out of the repo and inject them through the CI secret store.
