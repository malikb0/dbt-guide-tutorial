Your DAG usually stops at the last dbt model — but the value keeps flowing into a dashboard, a metric, a notebook or an app. Exposures declare those downstream consumers inside your dbt project, so the lineage graph finally answers the question every stakeholder asks: which model powers this number?

{{icon:lightbulb}}
An exposure is a declaration, not a transformation

An exposure does not run, test or store anything. It is a YAML node that names a downstream use — a dashboard, analysis, notebook, ML model or application — and records which dbt models and metrics it depends on. dbt uses it to draw lineage, to document the consumer and to power selection like +exposure:name.

The missing link in your DAG

Without exposures, the graph ends at the mart. You can see that fct_orders feeds nothing, because the dashboard lives in another tool. An exposure adds that external node, so the chain is complete from raw table to business surface.

What an exposure declares

A handful of properties describe each consumer. Only name, type and owner are required.

PropertyRequired?What it does
nameYesUnique snake_case identifier used in selection and docs.
typeYesOne of dashboard, notebook, analysis, ml or application.
ownerYesA name or email; additional properties are allowed.
depends_onExpectedList of refable nodes: ref(), source() or metric().
labelNoHuman-friendly name that may contain spaces and capitals.
urlNoAdds a “View this exposure” link in the generated docs site.
maturityNoConfidence level: high, medium or low.
description, tags, metaNoDocumentation and organization, same as other resources.
{{icon:triangle-alert}}
metric is not an exposure type

It is tempting to write type: metric, but the accepted types are dashboard, notebook, analysis, ml and application. To link an exposure to a metric, keep a normal type and reference the metric inside depends_on with metric('count_orders').

Writing an exposure

Exposures live under an exposures: key in any .yml file in your models/ directory. Here an e-commerce team maps a revenue dashboard and a lifetime-value analysis.

models/exposures.yml yaml 
version: 2

exposures:
  - name: weekly_revenue
    label: Weekly revenue dashboard
    type: dashboard
    maturity: high
    url: https://bi.example.com/dashboards/weekly-revenue
    description: Revenue by region for the weekly business review.
    owner:
      name: Analytics Team
      email: analytics@example.com
    depends_on:
      - ref('fct_orders')
      - ref('dim_customers')
      - source('ecommerce', 'orders')
    tags: ['finance']

  - name: customer_ltv_analysis
    label: Customer lifetime value analysis
    type: analysis
    maturity: medium
    description: Notebook exploring lifetime value by region.
    owner:
      name: Data Science Team
      email: data@example.com
    depends_on:
      - ref('dim_customers')
1
Create a YAML file

Add an exposures: key to any .yml file under models/. A single exposures.yml is fine to start.

2
Name the consumer

Set a snake_case name, a human label, a valid type, and the owning team’s email.

3
Point at the final models

List the marts the tool reads in depends_on using ref(), source() or metric().

4
Generate docs and select

Run dbt docs generate to see the new node, then target it with +exposure:name.

Linking to metrics

On projects that use the dbt Semantic Layer, an exposure can also depend on a metric. Metrics are defined elsewhere in the project; the exposure simply records that the downstream tool reads them.

models/exposures.yml yaml 
exposures:
  - name: revenue_tile
    label: Revenue tile
    type: dashboard
    owner:
      name: Finance Analytics
      email: finance-analytics@example.com
    depends_on:
      - metric('total_revenue')
      - ref('dim_regions')

Adding a metric() dependency does not compute the metric — it records a lineage edge so the docs graph, and selection, include it.

Where exposures show up

Once declared, exposures become first-class nodes you can select and document. They are especially useful in build commands: selecting everything that feeds one report is one short expression.

terminal bash 
# Rebuild and test everything upstream of one exposure
dbt build --select +exposure:weekly_revenue

# Just the tests that guard that exposure's models
dbt test --select +exposure:weekly_revenue

# List every declared exposure
dbt ls --resource-type exposure

# Render the docs site, including the exposure page and DAG
dbt docs generate

Guidelines

Don’t declare every ad-hoc query

Exposures are for consumers worth tracking: dashboards, published metrics, production ML features. One-off exploration does not need a YAML node.

Keep depends_on pointed at the final model

List the marts the tool actually reads, not every intermediate model in the chain — dbt resolves the rest of the lineage through ref().

Use label for humans, name for code

name must be snake_case and unique; label can be “Weekly revenue dashboard”. Docs show the label; selection uses the name.

Keep owners current

An exposure owned by a departed team member is worse than no exposure. Review ownership periodically; a name or email is required.
