You will often hear that “dbt caches your models.” That phrasing is convenient and misleading. dbt has no result cache that silently returns yesterday’s answer. What it actually has is a record of the last build — the state — plus materializations that persist data, so it can rebuild only what changed and process only new rows. Understand those two ideas and you understand most dbt performance work.

{{icon:lightbulb}}
What “caching” really means in dbt

Two distinct mechanisms get loosely called caching. State-based selection uses a saved manifest to find models whose code changed and rebuild them (and their children). Incremental models keep their existing table and insert or merge only new rows. Neither one is a query-result cache; your warehouse may have its own, and that is a separate topic.

The mythThe reality
“dbt caches query results.”No. dbt rebuilds the models you select; it does not serve cached results.
“dbt only reruns changed models automatically.”Only if you pass a state selector; a bare dbt run rebuilds every selected model.
“dbt adds the incremental WHERE for you.”No. You must write the is_incremental() filter yourself.
“Incremental models are always faster.”Usually, but late-arriving or updated rows need the right strategy.

State: the manifest remembers the last build

Every dbt invocation writes a manifest to target/manifest.json. It contains a content hash of every model, macro, seed, test and source. On a later run you can point dbt at a previous manifest and ask it to select only what changed.

terminal bash 
# Compare this project against the manifest produced by the last
# production run, then build changed models and everything downstream.
dbt build --select state:modified+ --state ./prod-manifest

In CI the pattern is to download the manifest produced by the last deployment, save it to a folder, and pass that folder to --state. A changed staging model selects itself and every model that depends on it.

Selection syntax that saves work

State selection is only one tool. The graph operators in the selection syntax decide how much of the DAG travels with each match.

SelectorWhat it selectsUse it when…
state:modifiedNodes whose code changed since the saved manifestYou want the smallest safe change set
state:modified+Modified nodes plus all their childrenTypical CI/CD build of a changed branch
+state:modifiedModified nodes plus all their parentsYou need the upstream chain too
source_status:fresher+Models downstream of sources that refreshedRebuild only when the raw data moved
result:error+Nodes that failed plus their childrenRecover after a partial run
+exposure:weekly_revenueEverything that feeds one exposureRefresh a single downstream report
{{icon:braces}}
A plus sign has a direction

state:modified+ reads left to right: changed nodes, then downstream. +state:modified reads right to left: upstream, then the changed nodes. When in doubt, run dbt ls --select … to preview exactly what will be built before you build it.

Incremental models: the real performance win

State selection avoids rebuilding unchanged models. Incremental materializations go further: instead of replacing a large table, they keep it and process only the new rows. The first run builds the full table; every later run runs your filtered SELECT and merges the delta.

models/fct_orders.sql sql 
{{ config(
    materialized='incremental',
    unique_key='order_id',
    incremental_strategy='merge'
) }}

select
    order_id,
    customer_id,
    order_date,
    quantity * unit_price as line_total
from {{ ref('stg_orders') }}

{% if is_incremental() %}
where order_date > (select max(order_date) from {{ this }})
{% endif %}
{{icon:triangle-alert}}
You write the filter, not dbt

dbt will not invent where order_date > max(…) for you. If you omit the {% if is_incremental() %} block, every run appends or merges the entire source again. The filter is the model author’s responsibility.

is_incremental() is true only when the model already exists as a table, is materialized as incremental, and the run is not a full refresh. That single condition lets the same file serve both the first full load and every later delta.

1
First run

is_incremental() is false, so the filter is skipped and dbt builds the whole table.

2
Later runs

The filter applies, so only rows newer than the current maximum are read and merged on unique_key.

3
Logic change

Run dbt build --full-refresh --select fct_orders to rebuild the table from scratch and discard the old rows.

Choosing a materialization

Incremental is not the default for a reason. Pick the simplest materialization that meets your freshness and cost needs.

MaterializationStorageRebuildBest for
ViewNoneEvery queryLight staging models that are always fresh
TableFull copyEvery runMarts queried often, where read speed matters
IncrementalExisting tableOnly new rowsLarge fact tables that grow over time

Reducing scanned bytes

Materialization strategy decides when you build. Query shape decides how much the warehouse reads each time — and that is often where the biggest wins hide.

{{icon:columns-3}}
Select only what you need

Replace select * with the columns the downstream model actually uses; wide scans cost more.

{{icon:filter}}
Filter and join early

Push where and joins into CTEs so later stages process fewer rows, not more.

{{icon:scan-line}}
Prune partitions

Filter on the partition column and the warehouse reads only the slices a query needs.

{{icon:database-zap}}
Lean on clustering

Clustering or sort keys co-locate frequently filtered columns so scans skip whole blocks.

Watch out for these

Changing model logic without a full refresh

Incremental models only touch new rows. If you change a calculation, old rows keep the old formula until you run --full-refresh. Version the change and schedule the rebuild deliberately.

Late-arriving rows

A row dated last week that lands today is older than max(order_date), so the filter skips it. Widen the window with a lookback — for example order_date >= (select max(order_date) from {{ this }}) - interval '3' day — and let unique_key merge duplicates.

Mutable rows that update in place

If a row’s values can change after it is loaded, pure append loses the update. Use a unique_key with a merge or delete+insert strategy, or snapshot the source to preserve history.

Trusting state selection for data freshness

state:modified compares code, not data. A model whose source changed but whose SQL did not will be skipped. Pair it with source_status:fresher+ or a scheduled full build.

Key takeaways

  • {{icon:circle-check}}dbt has no result cache. “Caching” really means state-based selection plus incremental materializations.
  • {{icon:circle-check}}Point --state at a previous manifest and use state:modified+ to rebuild only changed models and their children.
  • {{icon:circle-check}}You write the {% if is_incremental() %} filter; dbt will not add a WHERE clause on its own.
  • {{icon:circle-check}}--full-refresh rebuilds an incremental model from scratch — required when its logic changes.
  • {{icon:circle-check}}Query shape matters too: narrow columns, early filters and partition pruning cut scanned bytes.
