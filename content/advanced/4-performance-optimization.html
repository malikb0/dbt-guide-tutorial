At ten million rows everything still feels instant. At two hundred million, a full table scan per model turns a ten-minute build into a two-hour one. This lesson is about the two levers that fix it: compute less (incremental strategies and dbt state) and read less (partitioning, clustering and pruning).

{{icon:gauge}}
The performance philosophy: only rebuild what changed

Two independent savings compound. dbt's state tracking skips models whose definition has not changed; an incremental model skips the rows it already processed. Neither happens automatically for your data — you configure both.

Read less: partitioning and clustering

A partition physically splits a table into slices, usually by date. When a query filters on the partition column, the warehouse reads only the matching slices and prunes the rest. Clustering then sorts data within each partition so common filters and joins skip blocks too.

{{diagram:partition|A query for one month reads one partition instead of the whole table.}}

If your warehouse supports them, declare both in the model config. Here an orders fact is partitioned by order date and clustered by customer:

models/marts/fct_orders.sql sql 
{{ config(
    materialized='incremental',
    unique_key='order_id',
    partition_by={'field': 'order_date', 'data_type': 'date'},
    cluster_by=['customer_id']
) }}

select
    order_id,
    customer_id,
    order_date,
    quantity * unit_price as order_total
from {{ ref('stg_orders') }}

{% if is_incremental() %}
where order_date >= (select max(order_date) from {{ this }})
{% endif %}
{{icon:triangle-alert}}
Partitioning is warehouse-specific

partition_by and cluster_by are supported by BigQuery, Snowflake, Databricks/Spark and others — not by DuckDB, which has neither concept. Check your adapter's page before copying this config; on an unsupported adapter the keys are simply inert.

Compute less: incremental strategies

An incremental model only runs its query to produce new rows. The incremental_strategy decides how those rows land in the existing table, and each strategy trades correctness against speed and warehouse support.

{{diagram:materializations|Incremental is the materialization built for growing tables; the strategy controls how new rows are merged in.}}
StrategyWhat dbt doesNeeds unique_keyBest for
appendInserts the new rows; never updates or deletes.NoImmutable event logs that only grow.
mergeUpdates matching keys and inserts the rest (an upsert).YesMutable rows; the default on most adapters.
delete+insertDeletes rows whose keys appear in the new batch, then inserts them.YesWarehouses without a native MERGE.
insert_overwriteReplaces whole partitions covered by the batch.NoPartitioned tables on BigQuery/Spark.

Upsert with merge

When a row can change — an order's status, a customer's region — you want the new version to replace the old one. merge matches on unique_key and updates in place.

models/fct_order_status.sql sql 
{{ config(
    materialized='incremental',
    unique_key='order_id',
    incremental_strategy='merge'
) }}

Replace with delete+insert

The portable alternative when MERGE is unavailable. dbt deletes the affected keys, then inserts the fresh rows in one transaction.

models/fct_events.sql sql 
{{ config(
    materialized='incremental',
    unique_key='event_id',
    incremental_strategy='delete+insert'
) }}

For append-only logs, drop unique_key and use append — it is the fastest option because the warehouse does no matching at all:

models/events.sql sql 
{{ config(
    materialized='incremental',
    incremental_strategy='append'
) }}

select event_id, event_type, occurred_at
from {{ source('ecommerce', 'events') }}

Writing the incremental filter yourself

This is the single most common misconception about incremental models. dbt does not add a WHERE clause for you. If you tell dbt a model is incremental but write an unbounded SELECT, every run reprocesses the entire source and appends it again.

You are responsible for the filter, wrapped in the is_incremental() test so it only applies after the first build:

models/fct_orders.sql (excerpt) sql 
select order_id, customer_id, order_date, order_total
from {{ ref('stg_orders') }}

{% if is_incremental() %}
where order_date >= (select max(order_date) from {{ this }})
{% endif %}
{{icon:filter}}
What is_incremental() actually checks

It is true only when three things hold: the model is already materialized as a table in the warehouse, the current run is not --full-refresh, and the model's materialization is incremental. On the very first run it is false, so the model builds the full table — then every later run sees the filter.

{{diagram:cache|State tracking and the incremental filter attack different waste: unmodified models are skipped, and processed rows are not scanned again.}}

Threads and concurrency

dbt builds independent models in parallel, up to the number of threads configured for the target. On an eight-core warehouse, more threads can cut wall-clock time dramatically — until the warehouse saturates and every query slows down together.

Set threads per output in profiles.yml, and keep dev modest so a laptop-sized warehouse is not overwhelmed.

profiles.yml yaml 
outputs:
  prod:
    type: duckdb
    path: prod.duckdb
    schema: analytics
    threads: 8
{{icon:sliders-horizontal}}
More threads is not linearly faster

Start at four, raise until the warehouse's CPU or concurrency limit is the bottleneck, then stop. You can also override per invocation with --threads, which is handy in CI where the runner is small.

{{icon:terminal}} Try itterminal
terminal bash 
dbt build --threads 8 --select fct_orders+

dbt prints Concurrency: 8 threads and starts up to eight independent nodes at once. If the warehouse begins queueing, drop the number rather than adding more.

Rebuilding on purpose with --full-refresh

Sometimes the delta is not enough. When you change an incremental model's logic, its unique_key, or a column's type, the existing table is stale and only a full rebuild will do. --full-refresh drops and recreates the affected incremental models:

terminal bash 
dbt build --full-refresh --select fct_orders+

Because a full refresh ignores the incremental branch on that run, the model executes its unbounded SELECT and rebuilds from the source. For schema drift on incremental models, control what happens when columns change:

dbt_project.yml yaml 
models:
  dbt_shop:
    +on_schema_change: append_new_columns

Accepted values are ignore (the default), fail, append_new_columns and sync_all_columns. Pick fail when a surprise schema change should stop the run instead of silently drifting.

Key takeaways

  • {{icon:circle-check}}Partition and cluster large tables so filtered queries scan only the slices they need.
  • {{icon:circle-check}}append is fastest for immutable logs; merge upserts mutable rows; delete+insert is the portable fallback.
  • {{icon:circle-check}}dbt never adds the incremental WHERE for you — write it inside {% if is_incremental() %}.
  • {{icon:circle-check}}Tune threads to the warehouse, not the model count; more concurrency eventually hurts.
  • {{icon:circle-check}}--full-refresh rebuilds incremental models from scratch after logic or schema changes.
  • {{icon:circle-check}}Control schema drift with on_schema_change rather than discovering it in a dashboard.
