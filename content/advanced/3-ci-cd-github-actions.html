A CI/CD pipeline is a promise: nothing reaches production until it has been built and tested on an isolated copy of the warehouse. This lesson writes a real .github/workflows/dbt.yml — a slim CI job that rebuilds only what a pull request changed, plus a deploy job on main that produces the manifest every future PR defers to.

{{icon:workflow}}
CI verifies, CD promotes

Continuous integration proves a change is safe: compile it, build it on a throwaway schema, run its tests. Continuous delivery takes the artifact that passed and publishes it to production. Keep the two jobs separate so a failed test can never deploy.

The shape of a dbt CI pipeline

Every pull request triggers the same loop. A developer opens a PR, GitHub runs the workflow on a fresh runner, and the result appears as a check on the PR. If the check is red, the merge button is effectively blocked.

A complete workflow file

Two jobs live in one file. The ci job runs on pull requests; the deploy job runs on pushes to main and uploads the production manifest that later PRs compare against.

.github/workflows/dbt.yml yaml 
name: dbt CI/CD

on:
  pull_request:
    branches: [main]
  push:
    branches: [main]

concurrency:
  group: dbt-${{ github.workflow }}-${{ github.ref }}
  cancel-in-progress: true

env:
  DBT_PROFILES_DIR: .

jobs:
  ci:
    if: github.event_name == 'pull_request'
    runs-on: ubuntu-latest
    permissions:
      contents: read
      pull-requests: write
      actions: read
    env:
      DBT_TARGET: ci
      DBT_CI_SCHEMA: ci_pr_${{ github.event.pull_request.number }}
    steps:
      - name: Checkout the pull request
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip

      - name: Install dbt and the adapter
        run: pip install -r requirements.txt

      - name: Install dbt packages
        run: dbt deps

      - name: Find the latest production run
        id: prod-run
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: |
          RUN_ID=$(gh run list --workflow dbt.yml --branch main \
            --status success --limit 1 --json databaseId \
            --jq '.[0].databaseId')
          if [ "$RUN_ID" = "null" ]; then RUN_ID=""; fi
          echo "run-id=$RUN_ID" >> "$GITHUB_OUTPUT"

      - name: Download the production manifest
        if: steps.prod-run.outputs.run-id != ''
        uses: actions/download-artifact@v4
        with:
          name: prod-manifest
          path: ./prod-state
          repository: ${{ github.repository }}
          run-id: ${{ steps.prod-run.outputs.run-id }}
          github-token: ${{ secrets.GITHUB_TOKEN }}

      - name: Build modified models and their children
        run: |
          if [ -f ./prod-state/manifest.json ]; then
            dbt build --select state:modified+ \
              --defer --state ./prod-state --target ci
          else
            echo "No production manifest yet — running a full CI build."
            dbt build --target ci
          fi

      - name: Upload CI artifacts
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: ci-artifacts
          path: |
            target/manifest.json
            target/run_results.json
          if-no-files-found: warn

  deploy:
    if: github.event_name == 'push'
    runs-on: ubuntu-latest
    env:
      DBT_TARGET: prod
    steps:
      - name: Checkout main
        uses: actions/checkout@v4

      - name: Set up Python
        uses: actions/setup-python@v5
        with:
          python-version: "3.12"
          cache: pip

      - name: Install dbt and the adapter
        run: pip install -r requirements.txt

      - name: Install dbt packages
        run: dbt deps

      - name: Build production
        run: dbt build --target prod

      - name: Publish the production manifest
        uses: actions/upload-artifact@v4
        with:
          name: prod-manifest
          path: target/manifest.json
          if-no-files-found: error

Pair it with a tiny pinned requirements file so the pip cache has something to key on:

Understanding the three flags that make slim CI work

The magic is entirely in --select state:modified+, --defer and --state. Together they rebuild the smallest safe slice of the DAG.

{{diagram:cache|dbt compares the current project to the state manifest: only modified models and their children rebuild.}}

state:modified+

dbt hashes each node's config and compiled SQL. state:modified selects the nodes whose hash changed since the state manifest was written; the trailing + adds every downstream child that depends on them. That is the set that must be rebuilt to keep the warehouse correct.

--defer --state

--state points at the directory holding the production manifest.json. With --defer, any ref() to an upstream model that is not part of the selection resolves to the production relation instead of a table that does not exist in the CI schema. You build the delta; dbt reads the rest from prod.

{{icon:shield-check}}
Why a dedicated CI schema?

The job sets DBT_CI_SCHEMA=ci_pr_<number>, so every pull request builds into its own schema (for example analytics.ci_pr_412). Reviewers can inspect the result, and one PR can never overwrite another — or production.

{{icon:database}}
Reality check: deferral needs a shared warehouse

Slim CI assumes every target connects to the same database. On Snowflake or BigQuery, --defer reads unchanged models straight from the persistent production schema. A local DuckDB file on an ephemeral runner has no production data to defer to, so treat the flags here as the mechanism to learn and run a full dbt build when working purely locally.

{{icon:terminal}} Try itterminal
terminal bash 
dbt ls --select state:modified+ --state ./prod-state

dbt ls prints exactly which nodes the slim build would select. When a selection feels too large or too small, run this before you push.

Wiring the profiles and the target

The workflow sets DBT_PROFILES_DIR: ., so dbt reads a committed profiles.yml from the repo root. Each target declares its own schema and thread count; the CI schema comes from the environment variable the job set.

profiles.yml yaml 
dbt_shop:
  target: dev
  outputs:
    dev:
      type: duckdb
      path: dev.duckdb
      schema: analytics
      threads: 4
    ci:
      type: duckdb
      path: ci.duckdb
      schema: "{{ env_var('DBT_CI_SCHEMA', 'ci_local') }}"
      threads: 4
    prod:
      type: duckdb
      path: prod.duckdb
      schema: analytics
      threads: 8
{{icon:key}}
Never commit warehouse credentials

DuckDB needs none, which is why it is perfect for learning. For Snowflake, BigQuery or Postgres, keep secrets in GitHub encrypted secrets and read them in profiles.yml with {{ env_var('SNOWFLAKE_PASSWORD') }}. The profile file itself can stay in git when it contains only env references.

CI then CD: two jobs, one workflow

The deploy job is deliberately separate. It runs only on push to main, builds the full project with --target prod, and publishes target/manifest.json as the prod-manifest artifact. Every later pull request downloads that artifact and measures itself against it.

{{diagram:environments|The CI schema is disposable; production is the artifact that the next pull request defers to.}}
T+0
PR opened or updated

The ci job checks out the branch, installs dependencies, and downloads the last production manifest.

T+1
Delta build + tests

dbt build --select state:modified+ --defer --state rebuilds the changed slice on ci_pr_<number> and runs its tests.

T+2
Merge to main

The deploy job builds the full project against production and uploads a fresh manifest artifact.

Commenting results back on the pull request

The ci job already requests pull-requests: write. To leave a readable summary, parse target/run_results.json after the build and post it with the preinstalled GitHub CLI. The step must run with if: always() so it still comments when tests fail.

.github/workflows/dbt.yml (excerpt) yaml 
      - name: Comment run results on the PR
        if: always()
        env:
          GH_TOKEN: ${{ secrets.GITHUB_TOKEN }}
        run: |
          gh pr comment ${{ github.event.pull_request.number }} \
            --body "dbt CI: $(jq '.results | length' target/run_results.json) nodes executed."

Key takeaways

  • {{icon:circle-check}}A pull request should trigger a build and test run on an isolated schema before it can merge.
  • {{icon:circle-check}}state:modified+ rebuilds only changed nodes and their downstream children.
  • {{icon:circle-check}}--defer plus --state ./prod-state lets unbuilt upstream references read from production.
  • {{icon:circle-check}}Each PR gets its own CI schema so runs cannot collide with each other or with prod.
  • {{icon:circle-check}}The deploy job publishes manifest.json as the baseline the next PR compares against.
  • {{icon:circle-check}}Credentials belong in GitHub secrets and {{ env_var(...) }}, never in the committed profile.
