Most dbt mistakes are not made in the models — they are made at the boundary where raw data enters. Sources turn that boundary into something you can inspect: they name the upstream tables, record who loads them, test their shape, and measure how stale they are before a single model runs. This lesson makes your raw layer a first-class citizen.

{{icon:lightbulb}}
A source is a promise about data you don’t control

Unlike a model, a source is not built by dbt. {{ source('ecommerce', 'orders') }} tells dbt where an upstream table lives, creates a lineage edge, and lets you attach tests and freshness thresholds to it. You are asserting what the raw data should look like without owning the process that produces it.

Sources are the front door of the DAG

A model that selects from a source depends on it, exactly as it would depend on another model. dbt records the edge, orders the build correctly, and — critically — can warn you when that upstream table has stopped updating.

{{diagram:pipeline|Sources sit at the left edge: the raw tables dbt observes before any transformation begins.}}

Compared with a bare table name, a source declaration buys you four things:

{{icon:git-branch}}
Real lineage

The raw table appears in the DAG, so you can trace a metric all the way back to where it entered the warehouse.

{{icon:flask-conical}}
Testable assumptions

Run the same generic tests on source columns as on models — uniqueness, nulls, accepted values.

{{icon:clock}}
Freshness checks

dbt compares the newest timestamp to thresholds and warns or errors when data is late.

{{icon:book-open}}
Documentation

Descriptions and column metadata render into the generated docs site.

Declaring a source fully

Sources live under a sources: key in any .yml file in your models/ directory. This example documents the e-commerce raw tables, adds freshness thresholds and tests the key columns.

models/_sources.yml yaml 
version: 2

sources:
  - name: ecommerce
    database: raw
    schema: ecommerce
    loader: fivetran
    description: Raw tables loaded hourly from the application database.

    freshness:
      warn_after: {count: 12, period: hour}
      error_after: {count: 24, period: hour}
    loaded_at_field: _etl_loaded_at

    tables:
      - name: orders
        description: One row per order, including cancelled orders.
        columns:
          - name: order_id
            description: Primary key.
            data_tests:
              - unique
              - not_null
          - name: status
            data_tests:
              - accepted_values:
                  values: ['completed', 'cancelled', 'returned']

      - name: customers
        description: One row per customer.
        columns:
          - name: customer_id
            data_tests:
              - unique
              - not_null
{{icon:braces}}
Newer dbt moves freshness under config:

This tutorial targets the dbt 1.8 syntax, where freshness and loaded_at_field sit directly on the source. In newer releases (1.10+/v2) they move under a config: block on the source or table. The concepts — warn_after, error_after, loaded_at_field — are unchanged.

Source freshness

Freshness answers one question: when did this table last change? Give dbt a reliable timestamp column and thresholds and it can flag a stale pipeline before anyone queries it.

1
Pick the loaded-at column

loaded_at_field names the column the EL tool writes on every load. Without it (and without warehouse metadata), dbt cannot measure freshness.

2
Set warn and error thresholds

Each threshold is a count and a period such as {count: 12, period: hour}. Tables inherit the source-level values unless they override them.

3
dbt compares max(timestamp) to now

dbt runs dbt source freshness, which issues a small query — effectively select max(_etl_loaded_at) from … — and classifies each table as passing, warning or erroring.

Scope the check with the same selectors you use elsewhere: dbt source freshness --select source:ecommerce checks one source, and --select source:ecommerce.orders checks a single table. On a very large table a full max() scan can be expensive, so add a filter that limits the rows the freshness query reads — for example filter: _etl_loaded_at >= current_date - interval '2' day. For dbt 1.8 the command is dbt source freshness; newer releases also expose dbt freshness --resource-type source.

{{icon:triangle-alert}}
Freshness is not a test

dbt source freshness is a separate command from dbt test. A freshness warning does not fail dbt build unless you wire it into your orchestration. Results are written to target/sources.json; newer releases also emit target/freshness.json.

Testing sources

The data_tests in the source YAML run through the normal test command, but they are selected by source rather than by model.

terminal bash 
# Test every source table
dbt test --select "source:*"

# Test one source and all its tables
dbt test --select source:ecommerce

# Test one source table
dbt test --select source:ecommerce.orders

Generic tests on sources catch the failure modes that hurt most: a duplicated key, a null primary key, or a status value that was never agreed on. Because these run before downstream models, a dirty raw table fails fast instead of silently poisoning a mart.

Contracts at the source boundary

It is natural to want to “lock” the raw schema. dbt gives you three different mechanisms at this boundary, and they are not interchangeable.

MechanismWhat it checksWhere it lives
Generic testsValues: uniqueness, nulls, accepted sets, relationshipsSource columns in _sources.yml
FreshnessHow recently the table was loadedfreshness + loaded_at_field
Model contractNames and data_type of columnsThe staging model — not the source
{{icon:lock}}
Sources cannot be contracted

dbt model contracts — contract: {enforced: true} with column names and data_type — do not apply to sources. Contracts are supported for models materialized as table or view (and some incremental configurations), and dbt explicitly excludes sources, seeds and snapshots. Treat source columns and tests as documentation and validation, not enforcement.

So how do you enforce the shape of raw data? Put the contract on the first model that reads it. A staging model is thin, so its columns should mirror the source exactly — making it the natural place to pin names and types.

models/staging/stg_orders.yml yaml 
version: 2

models:
  - name: stg_orders
    config:
      contract:
        enforced: true
    columns:
      - name: order_id
        data_type: string
        constraints:
          - type: not_null
      - name: order_date
        data_type: date
      - name: status
        data_type: string

If the source renames a column or changes a type, the contract on stg_orders fails the build — which is the alarm you wanted. Contract support and the available constraint types vary by adapter, so confirm what your warehouse enforces.

Building only what moved

Freshness becomes powerful when it drives selection. Ask dbt to build just the models downstream of sources that refreshed, or everything downstream of one source, and explore the lineage from the command line.

terminal bash 
# Record which sources are fresher than last run, then build downstream
dbt source freshness
dbt build --select source_status:fresher+

# Build everything downstream of one source
dbt run --select source:ecommerce+

# List the source and its descendants, then render the full docs graph
dbt ls --select source:ecommerce+
dbt docs generate

Pitfalls to avoid

No loaded-at column

Freshness needs a timestamp the loader updates on every write. If you skip loaded_at_field, dbt cannot measure freshness and will simply skip the check.

Using a mutable timestamp as loaded-at

A business timestamp that updates when a row changes will make the source look permanently fresh even if the pipeline stopped. Use the timestamp written by the load process itself.

Testing sources only in production

Source tests belong in CI too. If a raw column is renamed upstream, you want the pull request — not a stakeholder — to find out first.

Assuming a contract on a source will enforce anything

It won’t — sources don’t support contracts. Enforce the schema on the staging model that reads the source, and use source tests for the data values.
