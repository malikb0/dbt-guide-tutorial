Running dbt build on your laptop is not deployment. Deployment is the discipline of turning a reviewed commit into trusted production tables — repeatably, with a record of what changed, who approved it, and a safe way to undo it.

{{icon:lightbulb}}
The deployment contract

Build the same code for every environment, prove it on staging before production, and gate the last step behind tests and an approval. Rollback should be another deploy — not a fire drill.

Environments are just named targets

In dbt Core an "environment" is not a separate product — it is a named output in your profiles.yml. Each output points at a different database file or warehouse, and usually a different schema. A single CLI flag chooses which one you build against.

{{diagram:environments|One codebase, three targets. The same commit is built for dev, validated in staging, then promoted to production.}}
EnvironmentWho runs itSchema / databaseFlag
devAnalytics engineers locallydbt_dev in a personal file--target dev
CI (staging-like)The pipeline onlya scratch schema rebuilt per pull request--target ci
productionThe CD job onlyanalytics, the serving layerdbt build --target prod

Notice that humans never build production locally. Separating the target from the person is what makes approvals and rollback possible later on this page.

profiles.yml yaml 
ecommerce:
  target: dev
  outputs:
    dev:
      type: duckdb
      path: dev.duckdb
      schema: dbt_dev
      threads: 4
    ci:
      type: duckdb
      path: ci.duckdb
      schema: dbt_ci
      threads: 4
    prod:
      type: duckdb
      path: "{{ env_var('DBT_PROD_PATH') }}"
      schema: analytics
      threads: 1
{{icon:key}}
Secrets never live in the repo

The committed profiles.yml references env_var('DBT_PROD_PATH'); the real value arrives from CI secrets or your shell in dev. Commit the shape, never the secret.

Build once, promote everywhere

People call two different things "the build": the compiled project — dbt's manifest.json, containing the DAG and rendered SQL — and the materialized tables in a warehouse. dbt promotes the first directly; the second is produced by running that manifest against a target.

{{diagram:pipeline|The deployable DAG is identical in every environment — only the target schema changes.}}

That distinction pays off in CI. A pull request can build the changed models into a scratch schema while deferring unchanged upstream models to production data. Reviewers see real results without paying to rebuild the entire warehouse.

macros/generate_schema_name.sql sql 
{% macro generate_schema_name(custom_schema_name, node) -%}
    {%- set default_schema = target.schema -%}
    {%- if custom_schema_name is none -%}
        {{ default_schema }}
    {%- else -%}
        {{ default_schema }}_{{ custom_schema_name | trim }}
    {%- endif -%}
{%- endmacro %}

This standard override means a model configured with schema: marts lands in dbt_dev_marts during development and analytics_marts in production — same code, environment-appropriate location.

CI: prove every pull request

Continuous integration answers one question: will this change break the warehouse? The job checks out the branch, installs dbt, then builds only what changed — plus everything downstream — into an isolated schema.

{{diagram:cicd|CI runs on the pull request; CD promotes to production after the merge.}}
1
Checkout and install

Restore the repo, install the pinned adapter, and run dbt deps so package versions match the lockfile.

2
Select what changed

--select state:modified+ compares the new manifest to a stored production manifest and picks the changed models plus all their children.

3
Build and test on a clone

dbt builds into a disposable CI schema and defers unchanged upstream models to production. Tests run against the result.

4
Report on the pull request

A failed test fails the job, so broken SQL never reaches main.

.github/workflows/dbt-ci.yml yaml 
name: dbt CI

on:
  pull_request:
    branches: [main]

jobs:
  build:
    runs-on: ubuntu-latest
    env:
      DBT_PROFILES_DIR: .
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: pip install "dbt-duckdb>=1.8"
      - run: dbt deps
      - name: Build changed models into a CI schema
        run: dbt build --target ci --select state:modified+ --defer --state ./prod-state
      - name: Test changed models
        run: dbt test --target ci --select state:modified+
{{icon:lightbulb}}
Store a production manifest to compare against

--defer --state needs a reference manifest. Download the latest manifest.json from your production run as a build artifact and feed it to CI so dbt knows what is genuinely new.

CD: deploy behind an approval

Continuous delivery deploys on merge to main. Production is a protected environment, so a person — or a policy — approves before any table changes.

.github/workflows/dbt-deploy.yml yaml 
name: dbt Deploy

on:
  push:
    branches: [main]

jobs:
  deploy:
    runs-on: ubuntu-latest
    environment: production        # required reviewers gate this job
    env:
      DBT_PROFILES_DIR: .
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.12'
      - run: pip install "dbt-duckdb>=1.8"
      - run: dbt deps
      - name: Deploy the full DAG to production
        run: dbt build --target prod
        env:
          DBT_PROD_PATH: ${{ secrets.DBT_PROD_PATH }}
{{icon:triangle-alert}}
dbt build is not just a run

It runs models, tests, snapshots and seeds in DAG order and stops the failing branch. That ordering is the safety net: a mart never rebuilds on top of a staging model whose tests just failed.

GateWhere it livesWhat it blocks
Lint + compileCISyntax and Jinja errors
Data tests on changed modelsCIWrong or missing rows before review
Peer reviewPull requestLogic and modelling mistakes
Environment approvalGitHub EnvironmentsUnreviewed production changes
Post-deploy verificationCDRegressions on the serving layer

Roll back by redeploying

Because models are defined in code, the fastest safe rollback is to redeploy the last known-good commit. Resist hand-editing production tables — that creates drift nobody can reproduce.

T+0
Alert fires

A dashboard shows revenue dropping minutes after a deploy.

T+2m
Freeze and assess

Stop the schedule, inspect run_results.json, and identify the offending commit.

T+5m
Redeploy the previous commit

Re-run the CD job against the prior tag, or restore the pre-deploy database snapshot.

T+15m
Confirm and write it up

Verify tests pass, then reopen the change as a new pull request with the fix.

FailureRollback move
Bad SQL in one modelRevert the model and redeploy the DAG; rebuild with --select that_model+
Wrong grain in a martRedeploy the previous commit; add the missing unique test before re-landing
Destructive full refreshRestore the warehouse snapshot, then re-run from the previous manifest
Silent bad dataRedeploy the last good manifest; the failing assertion becomes a permanent guard

Deploy subsets with selectors, not hope

Production deploys rarely run everything. Tags and selection syntax let you rebuild exactly what a change touches while leaving the rest untouched.

terminal bash 
# Rebuild models tagged nightly and everything downstream
dbt build --target prod --select tag:nightly+

# Deploy only changed models, comparing to the last production state
dbt build --target prod --select state:modified+

# Skip the slow marts and let the next scheduled run catch them
dbt build --target prod --exclude tag:heavy
{{icon:shield-check}}
Never --full-refresh blindly in production

A full refresh drops and rebuilds an incremental table. It is correct after a logic change to the incremental filter, but it is expensive and briefly leaves the table empty. Gate it behind a separate, approved job.

Key takeaways

  • {{icon:circle-check}}An environment is a named target in profiles.yml; --target prod is the whole switch.
  • {{icon:circle-check}}Promote the compiled manifest, then materialize it per environment with dbt build.
  • {{icon:circle-check}}CI builds state:modified+ into a scratch schema with --defer, so reviewers get results without a full rebuild.
  • {{icon:circle-check}}Gate production with a protected environment and an approval; dbt build already enforces DAG-order tests.
  • {{icon:circle-check}}Rollback is a redeploy of the last good commit, not a manual edit of production tables.
