Everything so far has been mechanics. This is judgment: how to structure a project, name things, review changes, document decisions, test at the right level, and which tempting patterns to ban outright. These conventions are what keep a warehouse trustworthy as a team grows.

{{icon:lightbulb}}
The maintainability test

A new analytics engineer should be able to answer "where does this number come from?" in under an hour, using only the repo and the docs site. Every convention on this page exists to make that true.

Layer the project: staging → intermediate → marts

A dbt project is a pipeline, and a pipeline has layers. Each layer has one job. Mixing those jobs is how warehouses rot.

{{diagram:layers|Raw sources feed staging, staging feeds intermediate logic, and intermediate feeds business-ready marts.}}
LayerIts one jobRules
staging/Clean one raw source tableOne source table per model; rename, cast, deduplicate only; no joins
intermediate/Reusable joins and business logicNot exposed to BI; may join staging models; still narrow in purpose
marts/Answer a business questionWide, documented, tested; the only layer BI is allowed to read
project layout tree 
models/
├── staging/
│   └── ecommerce/
│       ├── stg_ecommerce__orders.sql
│       ├── stg_ecommerce__customers.sql
│       └── _staging__models.yml
├── intermediate/
│   └── int_orders__joined.sql
└── marts/
    ├── core/
    │   ├── fct_orders.sql
    │   └── dim_customers.sql
    └── _marts__models.yml
{{icon:route}}
Dependencies only point downstream

Staging never references a mart. Intermediate never references a mart. If you feel the urge to build upward, you have found an intermediate model that belongs in its own layer.

One model, one purpose

The most common structural mistake is the "god model": 400 lines that join six sources, filter, aggregate and format, all at once. It is impossible to test, review or reuse. Split it with CTEs instead.

{{icon:circle-check}} Small, layered models
  • Each step is individually testable
  • A change touches one small file
  • Intermediate logic is reusable by several marts
  • Lineage shows exactly where a number comes from
{{icon:circle-x}} One giant model
  • Any test failure is hard to localize
  • Reviewers cannot reason about the whole file
  • Logic is duplicated because it cannot be reused
  • Every run rebuilds everything at once
models/marts/core/fct_orders.sql sql 
with orders as (
    select order_id, customer_id, order_date, line_total
    from {{ ref('stg_ecommerce__orders') }}
),

customers as (
    select customer_id, region, segment
    from {{ ref('stg_ecommerce__customers') }}
),

enriched as (
    select
        orders.order_id,
        orders.order_date,
        customers.customer_id,
        customers.region,
        customers.segment,
        orders.line_total
    from orders
    left join customers
        on orders.customer_id = customers.customer_id
)

select
    order_id,
    order_date,
    customer_id,
    region,
    segment,
    line_total
from enriched

Marts and the star schema

The mart layer is where you model for the business, not for the source system. The durable pattern is a star schema: narrow fact tables surrounded by conformed dimensions.

{{diagram:marts|A fact table at the grain of a business event, joined to dimensions that describe it.}}
ModelGrainNotes
fct_ordersOne row per orderNumeric measures and foreign keys; declared grain must be unique
fct_order_itemsOne row per order lineFiner grain than fct_orders; do not mix the two in one table
dim_customersOne row per customerDescriptive attributes; surrogate key, not just the natural key
dim_productsOne row per productSlowly changing attributes belong in a snapshot, not overwritten here
{{icon:boxes}}
State the grain in the first line of the description

"One row per order" is not decoration — it is the contract every downstream aggregate depends on. Test it with unique on the grain columns.

Naming conventions you can enforce

Names are the cheapest documentation you will ever write. Agree on them once, put them in CONTRIBUTING.md, and let review enforce them.

ThingConventionExample
Staging modelstg_<source>__<entity>stg_ecommerce__orders
Intermediate modelint_<subject>__<verb>int_orders__joined
Fact / dimensionfct_ / dim_ prefixfct_orders, dim_customers
Columnslowercase snake_caseorder_date, not OrderDate
Booleansis_ / has_ prefixis_active
Timestamps / dates_at / _date suffixcreated_at, order_date
Primary keys<entity>_id, uniqueorder_id
{{icon:table-properties}}
The double underscore is meaningful

In stg_ecommerce__orders, everything before __ is the source and everything after is the entity. It keeps names sortable and makes the origin of any model obvious at a glance.

Documentation is part of the code

Undocumented models are liabilities. dbt puts documentation in the same repo as the SQL, versioned and reviewed alongside it.

{{diagram:lineage|Generated docs and lineage let anyone trace a metric back through each model to its source table.}}
models/marts/_marts__models.yml yaml 
version: 2

models:
  - name: fct_orders
    description: One row per completed order. Grain is order_id.
    columns:
      - name: order_id
        description: Primary key.
        tests:
          - unique
          - not_null
      - name: customer_id
        description: Foreign key to dim_customers.
        tests:
          - relationships:
              to: ref('dim_customers')
              field: customer_id
      - name: order_status
        description: Lifecycle state of the order.
        tests:
          - accepted_values:
              values: ['completed', 'returned', 'pending']

Two commands turn that YAML into a searchable site. Run them in CI so docs are never stale:

terminal bash 
# Build the docs site from your project metadata
dbt docs generate

# Serve it locally to browse lineage and column descriptions
dbt docs serve
{{icon:triangle-alert}}
Document the why, not the obvious

order_date needs one line: which timezone, and which event. Don't restate the column name. Reviewers should reject a description that adds no information.

A testing strategy, not test theater

You do not need a test on every column. You need tests on the critical path and at the layer boundaries where a wrong assumption is expensive. Match the test to the layer.

LayerMinimum testsWhy
Sourcesnot_null + freshnessCatch upstream outages before they cascade
Stagingunique + not_null on the primary keyGuarantee one clean row per entity
IntermediateTests for the specific join or ruleAssert the logic the model exists to provide
Martsunique on grain, relationships, accepted_valuesProtect the numbers BI and executives consume

Severity decides what a failure does. Not every anomaly should halt the pipeline; but every warning should be visible and owned.

models/marts/_marts__models.yml yaml 
models:
  - name: fct_orders
    tests:
      - dbt_utils.expression_is_true:
          expression: "line_total >= 0"
          config:
            severity: warn
      - not_null:
          column_name: order_id
          config:
            severity: error
            store_failures: true
{{icon:flask-conical}}
A test nobody acts on is worse than no test

If a warning has fired every day for a month, it has trained the team to ignore the board. Fix the data, set severity: error, or delete the test and document why.

Code review that catches data bugs

A dbt pull request is a data contract change. Review the SQL, yes — but also the grain, the tests and the docs that ship with it.

1
Read the description and the grain

Does the model have a clear purpose and a stated grain? A vague description is a red flag for a vague model.

2
Check references, not table names

Every upstream must be a {{ ref(...) }} or {{ source(...) }}. A hardcoded schema breaks on the next environment.

3
Verify the tests match the change

A new primary key needs unique and not_null. A new foreign key needs relationships. A changed enum needs accepted_values.

4
Confirm CI is green and read the diff

The CI job already built and tested the changed models. Trust it, but confirm the reviewer sees the same lineage impact you do.

Review questionWhat good looks like
Is the model in the right layer?Staging cleans one source; marts answer a question
Is the grain unique?A unique test proves it
Are columns named consistently?snake_case, _at/_date, is_
Is anything undocumented?Model and non-obvious columns have descriptions
Could this have been an edit to an existing model?New models are justified, not accidental forks

Anti-patterns to ban

These are the habits that quietly turn a clean project into a legacy one. Name them in your style guide so review can point at a shared rule instead of personal taste.

  • {{icon:circle-x}}select * in a mart — schema changes leak into dashboards silently.
  • {{icon:circle-x}}Hardcoded table or schema names instead of {{ ref(...) }} and {{ source(...) }}.
  • {{icon:circle-x}}Business logic duplicated in the BI tool — two definitions, two different numbers.
  • {{icon:circle-x}}Untested marts and undocumented primary keys.
  • {{icon:circle-x}}God models that join, filter, aggregate and format in one file.
  • {{icon:circle-x}}A nightly --full-refresh in production to "make it work".
  • {{icon:circle-x}}Copy-pasting SQL between models instead of extracting a macro or intermediate model.
How many tests is enough?

Enough to protect the critical path and every layer boundary. Start with unique and not_null on primary keys, relationships on foreign keys, and freshness on sources. Add tests when a bug actually reaches production — each incident should leave a regression test behind.

When should a model be split?

When it has more than one clear purpose, when a downstream model only needs part of it, or when a reviewer cannot hold it in their head. Prefer CTEs within a model first; promote a CTE to its own model when it becomes reusable.

Do we need a custom materialization?

Almost never. Custom materializations are expert tools for logic the built-ins cannot express, such as external tables or specialised incremental patterns. If a table, view or incremental model with hooks can do it, use that. This is YAGNI applied to dbt.

One repo or one per domain?

Start with one repo and one project. Split into multiple projects only when team boundaries, release cadence or DAG size genuinely force it — cross-project refs add real coordination cost.

Single source of truth, enforced by convention

The point of all of this is trust: one definition of "revenue", one place to change it, one lineage to follow it. That is a social contract, and the repo is where you write it down.

Key takeaways

  • {{icon:circle-check}}Layer the project: staging cleans one source, intermediate holds reusable logic, marts answer business questions.
  • {{icon:circle-check}}One model, one purpose — split god models with CTEs, then promote reusable CTEs to models.
  • {{icon:circle-check}}Name consistently (stg_, int_, fct_, dim_, _at, is_) and put the rules in CONTRIBUTING.md.
  • {{icon:circle-check}}Document the grain and the why; generate and publish the docs site so it can never go stale.
