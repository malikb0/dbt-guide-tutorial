A materialization is the code that decides how a dbt model becomes a database object. view, table, incremental and ephemeral are not built into the SQL compiler — they are materialization macros. When none of them fits, you write your own and hook into dbt's lifecycle.

{{icon:dna}}
A materialization is a macro with a contract

It receives the compiled model SQL, prepares the database, runs pre- and post-hooks, executes the SQL, cleans up, and returns the relations it created. Everything dbt does with a model is defined here.

The materialization you already use

Every built-in strategy trades freshness, storage and speed. Custom materializations extend that list for cases the four defaults cannot express.

{{diagram:materializations|View, table, incremental and ephemeral are the built-ins; a custom materialization adds a fifth option of your own design.}}

The lifecycle dbt runs

Whether it is the built-in table or your macro, the same phases run in order. Knowing the order is what lets you place hooks correctly.

1
Prepare

Look up the existing relation and decide whether to drop, back up or leave it in place.

2
Pre-hooks

Run the model's configured pre_hook statements.

3
Build

Execute the model SQL through a statement('main') block to create or modify the relation.

4
Post-hooks

Run post_hook statements such as grants or statistics.

5
Return relations

Return the relations created so dbt can update its relation cache.

Writing your own materialization

Materialization macros live in macros/ and use {% materialization %} instead of {% macro %}. The second argument binds it to an adapter (default is the fallback). The special variable sql holds the compiled model query; pre_hooks and post_hooks are injected automatically.

macros/materializations/my_table.sql sql 
{% materialization my_table, default %}

  {%- set target_relation = api.Relation.create(
        identifier=this.identifier,
        schema=this.schema,
        database=this.database,
        type='table') -%}

  {%- set existing_relation = adapter.get_relation(
        database=this.database,
        schema=this.schema,
        identifier=this.identifier) -%}

  {%- if existing_relation is not none and existing_relation.type != 'table' -%}
    {%- do adapter.drop_relation(existing_relation) -%}
  {%- endif -%}

  {{ run_hooks(pre_hooks) }}

  {% call statement('main') %}
    {{ create_table_as(False, target_relation, sql) }}
  {% endcall %}

  {{ run_hooks(post_hooks) }}

  {{ adapter.commit() }}

  {{ return({'relations': [target_relation]}) }}

{% endmaterialization %}

Read the built-ins before you write one

The table, view and incremental materializations ship with dbt. They are the best reference for relation handling, --full-refresh behaviour and cache updates — copy their structure rather than starting from a blank file.

Inspecting relations with get_columns_in_relation

To make schema-aware decisions — backfill a column, sync new columns, or skip work when nothing changed — query the existing relation's shape with adapter.get_columns_in_relation(relation). It returns Column objects with .name, .data_type and helpers such as .is_numeric().

macros/column_audit.sql sql 
{% macro column_audit(relation) %}
    {%- set columns = adapter.get_columns_in_relation(relation) -%}
    {%- for column in columns %}
    {%- if column.is_numeric() %}
    -- numeric: {{ column.name }} ({{ column.data_type }})
    {%- endif %}
    {%- endfor %}
{% endmacro %}

Use it inside a materialization to compare the target and the incoming data, then choose an append_new_columns, sync_all_columns or full-rebuild path. This is exactly how dbt's incremental on_schema_change logic works under the hood.

Pointing a model at it

The model itself is unchanged: a plain SELECT. Only the materialized config changes to the name of your materialization.

models/fct_orders.sql sql 
{{ config(materialized='my_table') }}

select
    order_id,
    customer_id,
    order_date,
    quantity * unit_price as order_total
from {{ ref('stg_orders') }}

Notice what the model does not contain: no DDL, no CREATE, no persistence logic. That belongs to the materialization and stays reusable across every model that selects it.

Hooks: pre_hook and post_hook

Hooks are SQL statements dbt runs around a model. pre_hook fires before the materialization builds the relation; post_hook fires after. Each accepts a single string or a list, and hooks can reference {{ this }} to target the model being built.

models/fct_orders.sql sql 
{{ config(
    materialized='my_table',
    pre_hook="insert into audit_log values ('fct_orders', current_timestamp, 'started')",
    post_hook=[
      "insert into audit_log values ('fct_orders', current_timestamp, 'complete')",
      "analyze {{ this }}"
    ]
) }}

select order_id, customer_id, order_date, order_total
from {{ ref('stg_orders') }}
{{icon:triangle-alert}}
Hooks fail the model if they fail

If a pre_hook errors, the model never builds; if a post_hook errors, the model is marked as failed (and, on transactional warehouses, rolled back). Keep hooks small, idempotent and free of long-running DDL.

Project-wide hooks: on-run-start and on-run-end

Sometimes the hook is not about one model but about the whole invocation. Declare on-run-start and on-run-end in dbt_project.yml. The end hook has extra context: results (one per executed node) and schemas (the schemas touched).

dbt_project.yml yaml 
on-run-start:
  - "{{ log('dbt run starting', info=True) }}"

on-run-end:
  - "{% for schema in schemas %} grant usage on schema {{ schema }} to role reporter; {% endfor %}"
  - "{{ log('built ' ~ results | length ~ ' nodes', info=True) }}"

Use on-run-start for session settings and logging; use on-run-end for grants, statistics, and audit rows that depend on the whole run finishing. For a hook that belongs to a folder rather than a single model, set it under models: with a + prefix in dbt_project.yml.

When a custom materialization is worth it

{{icon:circle-check}} Pros
  • Expresses persistence patterns dbt does not ship (external tables, partition swaps, special indexes).
  • Reusable: write once, apply to many models through config.
  • Encapsulates prepare/build/cleanup so models stay pure SQL.
{{icon:circle-x}} Cons
  • Advanced and adapter-specific; small mistakes corrupt or strand tables.
  • You own caching, commits and --full-refresh behaviour.
  • Overriding built-in names can break every model in the project.
{{icon:lightbulb}}
Prefer the built-ins first

Reach for a custom materialization only when config, hooks and the standard strategies genuinely cannot express the requirement. Always return the created relations and commit your transaction, or dbt will roll the work back and warn about its cache.
