Expert-Level Query Optimization

Partition pruning, materialized caches, micro-batching and reading the query plan like a DBA.

Your progress

At expert level, performance is not guessing — it is measurement. You read the query plan, prune the partitions the warehouse never needed, choose the right incremental strategy, and put a real cache in front of the expensive work. This page is about the evidence behind every optimization.

No optimization without a baseline

A model that "feels slow" is not a fact. Capture bytes scanned, compute time and wall-clock duration before you change anything, or you will never know which change mattered.

Measure first: the numbers that matter #

Four metrics explain almost every performance complaint. They are not the same, and optimizing for one can hurt another.

I/O
bytes swept from storage — the number partition pruning attacks
CPU
shuffle, join and aggregation work — the number clustering attacks
wall
elapsed time a person waits — the number threads and batching attack
cost
credits or dollars billed — the number governance attacks

dbt already records the most accessible number for you: every node in run_results.json carries an execution_time. Sort by it to find the real offender — it is rarely the model everyone complains about.

MetricWhere to read itWhat it tells you
Bytes scannedQuery plan / warehouse query historyWhether pruning and column selection work
Execution time per nodetarget/run_results.jsonWhich model is the critical path
Rows and spillsEXPLAIN ANALYZEWhether the engine is doing more work than it should
Credits / bytes billedWarehouse query historyThe real bill — the constraint you are ultimately tuning
Tune the critical path, not every model

Making a fast model faster does nothing for total runtime. Only the slowest chain through the DAG moves the finish line, so start with the node on that chain.

Try itterminal
terminal bash 
# Rank the last run's models by execution time (seconds)
jq '.results
    | sort_by(.execution_time)
    | reverse
    | .[0:5]
    | map({model: .unique_id, seconds: .execution_time})' \
  target/run_results.json

Expected output: the five slowest nodes in the DAG. Optimize the one at the top of the list — it is the critical path others wait on.

Read the query plan like a DBA #

Every warehouse will show you what it intends to do before it does it. In dbt, compile the model to inspect the exact SQL that would run, then hand that SQL to the planner.

terminal bash 
# Render the model to pure SQL without running it
dbt compile --select fct_orders

# Then ask the warehouse what it would do with that SQL
dbt show --select fct_orders --limit 10

A DuckDB EXPLAIN ANALYZE reads bottom-up: scans first, then joins and aggregates. Sample output is abbreviated below — the operators and their row counts are the story.

query plan sql 
explain analyze
select
    order_date,
    region,
    sum(line_total) as revenue
from {{ ref('fct_orders') }}
where order_date >= date '2024-03-01'
group by 1, 2;

-- ┌─────────────────────────┐
-- │ HASH_GROUP_BY           │  2.1k rows out
-- │   FILTER                 │  pushed into scan ✓
-- │     TABLE_SCAN fct_orders│  1.2M rows scanned
-- └─────────────────────────┘
Full scan where a seek was possible

The plan scans every row because the predicate does not align with the partitioning or index.

Nested loop over a large table

A loop join on millions of rows usually means a missing join key or a stale statistic.

Spilling to disk

The aggregation exceeded memory and swapped out. Reduce columns or add a pre-aggregate.

Row estimate far from reality

A 100× misestimate means the planner chose the wrong strategy. Refresh statistics.

Partition pruning #

Partitioning splits a large table into slices by a column — usually a date. When a query filters on that column, the engine reads only the matching slices. This is the single biggest I/O win available on multi-million-row facts.

The dbt config is adapter-specific. The key is that the partition column is declared in the model and the query filter lines up with it.

models/marts/fct_orders.sql sql 
{{ config(
    materialized='incremental',
    partition_by={'field': 'order_date', 'data_type': 'date'},
    cluster_by=['customer_id']
) }}

select
    order_id,
    customer_id,
    order_date,
    line_total
from {{ ref('stg_ecommerce__orders') }}
{% if is_incremental() %}
where order_date > (select max(order_date) from {{ this }})
{% endif %}
Never wrap the partition column in a function

where date_trunc('month', order_date) = ... prevents pruning — the engine must compute the function for every row. Filter on the raw column range instead so the slices can be skipped.

AdapterPruning mechanismdbt config
BigQueryPartitioned + clustered tablespartition_by, cluster_by
SnowflakeMicro-partitions + clustering keyscluster_by
DatabricksDelta partitions / liquid clusteringadapter-specific clustering config
PostgresDeclarative partitions or indexeshandled in DDL, not a dbt model config
DuckDBZone maps on ordered columnsno partition_by; rely on predicates and sorting

Pick the right incremental strategy #

An incremental model rebuilds only the new or changed rows. How it merges those rows is the strategy, and the correct choice depends on whether rows are append-only or mutable.

StrategyBehaviorUse when
appendInsert new rows onlyImmutable events — logs, clickstream, raw invoices
mergeUpsert by unique keyRows change status over time — orders, subscriptions
delete+insertDelete matching keys, then insertMutable partitions on engines where merge is costly
insert_overlayReplace whole partitionsPartitioned tables rebuilt by date window
microbatchProcess disjoint time batchesVery large time-series facts and easy backfills
unique_key is the contract

For merge and delete+insert, dbt needs a key. If the key is not truly unique, the merge silently fans out rows. Test it with unique before trusting the strategy.

Micro-batch the truly enormous models #

Microbatch is an incremental strategy for time-series facts that are too large to process in one pass. Instead of one giant filter, dbt splits the work into disjoint batches by an event-time column — one day at a time by default — and tracks which batches are complete.

models/marts/fct_events.sql sql 
{{ config(
    materialized='incremental',
    incremental_strategy='microbatch',
    event_time='event_at',
    batch_size='day',
    lookback=1
) }}

select
    event_id,
    customer_id,
    event_at,
    event_type
from {{ ref('stg_ecommerce__events') }}

Because each batch is independent, a failed run only reprocesses its window, and backfills become surgical. dbt exposes the window on the CLI:

terminal bash 
# Backfill a specific range of event time, day by day
dbt run --select fct_events \
  --event-time-start "2024-01-01" \
  --event-time-end "2024-02-01"
Microbatch respects late data with lookback

lookback=1 reprocesses one prior batch, so a late-arriving event is captured on the next run instead of being missed forever.

Materialized caches, defined honestly #

"Cache" is overloaded. There are three distinct things, and confusing them leads to tuning the wrong layer.

KindWhat it cachesInvalidated by
Warehouse result cacheIdentical query resultsAny change to underlying data or SQL
Table / incremental materializationComputed result rows on diskThe next dbt build of that model
Materialized viewRows the warehouse refreshes for youWarehouse refresh policy or base-table writes
dbt state cacheThe build decision, via state hashes--select state:modified comparing manifests
dbt's "cache" only skips builds

When dbt says only changed models rebuild, it is comparing hashes in the manifest — it is not caching data. The data cache is whatever materialization you chose: table, incremental, or a warehouse materialized view.

The classic server-side cache is a pre-aggregated mart. It stores a smaller, already-summarized result that BI can query cheaply, refreshed on its own schedule.

models/marts/agg_revenue_by_day.sql sql 
-- A 365-row answer to a question BI asks a hundred times a day.
{{ config(materialized='table') }}

select
    order_date,
    region,
    count(distinct order_id) as orders,
    sum(line_total) as revenue
from {{ ref('fct_orders') }}
group by 1, 2

Threads and concurrency #

dbt runs independent DAG branches in parallel using threads. More threads is not automatically faster — past the warehouse's own concurrency limit, extra threads just queue and contend.

profiles.yml yaml 
prod:
  type: duckdb
  path: /data/analytics_prod.duckdb
  schema: analytics
  threads: 1        # DuckDB allows a single writer to the file
WarehouseThreads guidanceWhy
DuckDB / SQLitethreads: 1Single-writer file locks; parallelism causes contention, not speed
PostgresRoughly CPU cores, modestEach thread opens a connection and competes for shared buffers
SnowflakeDo not exceed warehouse concurrencyExtra queries queue; scale the warehouse up instead
BigQueryThreads for API parallelismThe warehouse scales compute itself; threads only reduce client wait
Parallelism trades speed for blast radius

With many threads, a bad deploy changes many models at once before the first failure surfaces. On production, lower threads and --fail-fast give you a smaller failure surface.

Cost guardrails #

Performance work is incomplete until it is bounded. Tag every query so spend is attributable, and cap the runaway query before it bills you.

dbt_project.yml yaml 
query-comment:
  comment: 'dbt | {{ node.unique_id }} | {{ target.name }}'
  append: true
GuardrailWhat it limits
Query comments / tagsMakes cost attributable by model and environment
Warehouse budgets & alertsNotifies when daily spend crosses a threshold
Statement / job timeoutsKills a runaway query before it scans the whole table
Byte / credit capsRefuses a query whose estimate exceeds a ceiling
Scheduled heavy modelsMoves expensive rebuilds off the interactive path

Key takeaways #

  • Measure bytes scanned, compute, wall-clock time and cost before you touch anything.
  • Read the query plan: pushed-down filters, scan row counts, join strategy and spills are the culprits.
  • Partition pruning only works when the predicate uses the raw partition column, never a function around it.
  • Match the incremental strategy to the data shape: append for events, merge for mutable rows, microbatch for giant time series.
  • dbt's state is a build cache; data caching is a materialization decision.
  • Size threads to the warehouse and cap spend with query comments, timeouts and budgets.
