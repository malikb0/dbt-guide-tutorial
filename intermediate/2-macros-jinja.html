Macros & Jinja Templating

Stop copy-pasting SQL. Write reusable functions with Jinja macros and control flow.

Copy-pasting the same SQL between models is a quiet bug factory: fix it in one file and the others drift. Jinja — dbt's templating engine — lets you extract that logic into a macro, one reusable function you call from every model. Write it once, change it once.

A macro returns SQL text

Macros do not move data. They run while dbt compiles your project and hand back a string that gets spliced into the query. If you can write it in a SQL SELECT and you repeat it, it can be a macro.

The copy-paste problem #

Imagine three models all need to turn a region code into a friendly label. Without a macro, the same CASE expression is pasted into stg_orders, stg_customers and fct_sales. When marketing asks for a new region, you hunt down every copy — and miss one.

Macros are just Jinja files under macros/. Once defined, they are available to every model in the project — no import statement required.

Before and after: DRY in action #

The same requirement, written two ways. Switch tabs to compare.

The label logic is repeated in every model. Change the wording and you must remember all of them.

models/stg_orders.sql sql 
select
    order_id,
    region,
    case
        when region = 'North America' then 'US & Canada'
        when region = 'Europe' then 'EU'
        when region = 'Asia-Pacific' then 'APAC'
        else 'Other'
    end as region_label
from {{ ref('stg_customers') }}

-- ...and the exact same CASE is pasted into stg_customers.sql,
-- fct_sales.sql and every other model that needs a region label.

The logic moves into one macro. Models call it by name, and the next change happens in exactly one place.

macros/region.sql sql 
{% macro region_label(column_name) %}
    case
        when {{ column_name }} = 'North America' then 'US & Canada'
        when {{ column_name }} = 'Europe' then 'EU'
        when {{ column_name }} = 'Asia-Pacific' then 'APAC'
        else 'Other'
    end
{% endmacro %}
models/stg_orders.sql sql 
select
    order_id,
    {{ region_label('region') }} as region_label
from {{ ref('stg_customers') }}

Anatomy of a macro #

A macro is declared with {% macro %}, takes arguments with optional defaults, and ends with {% endmacro %}. Whatever Jinja renders between those tags becomes part of the compiled query.

macros/currency.sql sql 
{% macro cents_to_dollars(column_name, scale=2) %}
    round(cast({{ column_name }} as decimal(18, 2)) / 100, {{ scale }})
{% endmacro %}

Call it from any model, and it compiles to plain SQL:

models/stg_payments.sql sql 
select
    payment_id,
    {{ cents_to_dollars('amount_cents') }} as amount_usd,
    {{ cents_to_dollars('fee_cents', 4) }} as fee_usd
from {{ ref('stg_payments') }}
Arguments are just text

Jinja substitutes the argument where you write {{ column_name }}. Because the result is SQL text, keep quoting intentional: cents_to_dollars('amount_cents') passes the column name, not its value.

Loops: generate repeated SQL #

An e-commerce report often needs one revenue column per region. Instead of writing the same sum(case ...) by hand, loop over a list.

models/revenue_by_region.sql sql 
{% set regions = ['North America', 'Europe', 'Asia-Pacific'] %}

select
    order_date,
    {% for region in regions %}
    sum(case when region = '{{ region }}' then revenue else 0 end)
        as {{ region | replace(' ', '_') | lower }}_revenue{% if not loop.last %},{% endif %}
    {% endfor %}
from {{ ref('stg_orders') }}
group by 1

Two details matter: loop.last keeps the commas correct, and Jinja filters such as replace and lower turn a human label into a clean column alias.

Conditionals: change the SQL by context #

The {% if %} tag branches the compiled SQL. A common use is excluding test data outside production.

models/stg_orders.sql sql 
select
    order_id,
    customer_id,
    order_date,
    revenue
from {{ source('ecommerce', 'orders') }}

{% if not var('include_test_orders', false) %}
where is_test = false
{% endif %}
The same idea powers incremental models

The {% if is_incremental() %} block you met in materializations is just a conditional: dbt is asking "does this model already exist?" and your SQL answers accordingly.

Variables, var() and config() #

Jinja gives you a few ways to parameterize a project. Use var() for values that change between runs, and config() for model settings rather than data.

PatternExampleUse it for
{% set %}{% set tax = 0.2 %}A local value used inside one model or macro
var(){{ var('start_date', '2024-01-01') }}Project variables set in dbt_project.yml or --vars
config(){{ config(materialized='table') }}Model settings, not query values
env_var(){{ env_var('DBT_USER') }}Reading an environment variable at compile time
target.name{% if target.name == 'prod' %}Branching on the active target (dev, prod)
models/orders_since.sql sql 
{% set start_date = var('start_date', '2024-01-01') %}

select *
from {{ ref('stg_orders') }}
where order_date >= '{{ start_date }}'

Override the default from the command line without touching a file:

terminal bash 
dbt run --select orders_since --vars '{start_date: 2024-06-01}'

Using macros from packages: dbt_utils #

You don't have to write every macro. The community package dbt_utils ships hundreds of battle-tested ones. Declare it in packages.yml, then install it.

packages.yml yaml 
packages:
  - package: dbt-labs/dbt_utils
    version: [">=1.0.0", "<2.0.0"]
terminal bash 
dbt deps

Package macros are namespaced with the package name, so you can tell where a function came from:

models/order_lines.sql sql 
select
    {{ dbt_utils.generate_surrogate_key(['order_id', 'product_sku']) }} as order_line_key,
    {{ dbt_utils.star(from=ref('stg_orders'), except=['_loaded_at']) }}
from {{ ref('stg_orders') }}
dbt_utils macroWhat it generates
generate_surrogate_key()A stable hash key from one or more columns
star()All columns, optionally excluding some
pivot()Rows to columns for a known set of values
date_spine()A continuous date range for a calendar model
union_relations()Appends multiple relations with matching columns

Because project and package macros are global, a single definition can standardize a transformation across every layer of the project — staging and marts alike.

Macro hygiene #

Keep macros small and single-purpose

One macro should do one thing. A macro that formats, filters and aggregates is harder to reuse and test than three focused ones.

Whitespace control keeps compiled SQL readable

Jinja tags leave blank lines. Use {%- ... -%} to trim the surrounding whitespace when your generated SQL starts looking ragged.

Don't abstract something used once

A macro used in a single model is just indirection. Reach for one when the same pattern appears in several places.

Macros generate SQL; they don't transform data

Unless you deliberately use advanced features like run_query(), macros only assemble text. The warehouse still does the data work when the model runs.

Key takeaways #

  • A macro is a reusable Jinja function that returns SQL text at compile time — it does not move data.
  • Put macros in macros/*.sql with {% macro name(args) %} … {% endmacro %}; every model can call them.
  • {% for %} loops and {% if %} conditionals generate or branch SQL without copy-paste.
  • Use var('name', default) for per-run values and config() for model settings.
  • Install community macros with packages.yml + dbt deps, then call them namespaced, e.g. dbt_utils.star().
