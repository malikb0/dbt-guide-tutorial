Materializations: View, Table & Incremental

Choose how dbt persists each model — and understand the freshness, cost and performance trade-offs.

Your progress

A model's materialization answers one question: how should dbt persist the result of this SQL? Build a view, rebuild a table, append only new rows, or inline the logic as a CTE. It is the setting that most affects freshness, query cost and run time — so it deserves a deliberate choice, not a copy-paste.

A materialization is a storage decision

Your SELECT is always the same. The materialization decides what dbt does with it: store nothing, store a full copy, or store and maintain it incrementally.

The four materializations at a glance #

dbt ships four built-in materializations. They trade storage and build effort against freshness.

MaterializationWhat dbt createsFreshnessBest for
ViewA database view — no rows storedAlways freshLight transforms, early layers, fast iteration
TableA physical table, dropped and rebuiltFresh after each runExpensive joins and aggregations read often
IncrementalA table updated with only new or changed rowsFresh within the filterLarge event tables that keep growing
EphemeralNothing — inlined as a CTE where it is referencedNo object to querySmall reusable building blocks
The default is a view

If you never set a materialization, dbt creates a view. That is a safe default while developing: no storage cost and the result is always current.

The four types in detail #

Switch between the tabs to see how each one is configured and when it earns its keep.

A view stores the query, not the data. Every read re-runs it against the upstream models, so it is always up to date and uses no storage. The trade-off is that a costly view is recomputed on every dashboard query.

models/order_counts.sql sql 
{{ config(materialized='view') }}

select
    customer_id,
    count(*) as order_count
from {{ ref('stg_orders') }}
group by 1

A table materialization drops the old object and rebuilds it from scratch on every dbt run. Reads are fast because the work is already done, but you pay the full compute and storage cost each time.

models/customer_orders.sql sql 
{{ config(materialized='table') }}

select
    c.region,
    count(*) as total_orders,
    sum(o.quantity * o.unit_price) as revenue
from {{ ref('stg_orders') }} o
join {{ ref('stg_customers') }} c
    on o.customer_id = c.id
group by 1

An incremental model builds a table on the first run, then appends or merges only the rows you tell it to on later runs. It is the only materialization where you control which data is reprocessed — see the next section.

models/fct_orders.sql sql 
{{ config(
    materialized='incremental',
    unique_key='order_id'
) }}

select
    order_id,
    customer_id,
    order_date,
    quantity * unit_price as line_total
from {{ ref('stg_orders') }}

{% if is_incremental() %}
where order_date > (select max(order_date) from {{ this }})
{% endif %}

An ephemeral model never becomes an object in the warehouse. dbt compiles it into a CTE and pastes it into every model that references it. It is for tidiness, not for performance: heavy ephemeral logic is recomputed in each downstream model.

models/order_lines.sql sql 
{{ config(materialized='ephemeral') }}

select
    order_id,
    customer_id,
    quantity * unit_price as line_total
from {{ ref('stg_orders') }}

Incremental models: you write the filter #

This is the most misunderstood part of dbt, so read it twice. When a model is incremental, dbt does not automatically add a WHERE order_date > MAX(...) clause. The {% if is_incremental() %} block and its filter are written by you.

dbt does not add the incremental WHERE clause for you

Setting materialized='incremental' only changes how dbt writes rows into the existing table. If you omit the filter, every run inserts the entire query result again and you get duplicates. The filter below is your responsibility.

models/fct_orders.sql sql 
{{ config(
    materialized='incremental',
    unique_key='order_id',
    incremental_strategy='delete+insert'
) }}

select
    order_id,
    customer_id,
    order_date,
    quantity * unit_price as line_total
from {{ ref('stg_orders') }}

{% if is_incremental() %}
where order_date > (select max(order_date) from {{ this }})
{% endif %}

How the pieces fit together:

1
First run — full table

is_incremental() is false because the model does not exist yet, so the where is skipped and dbt builds the whole table.

2
Later runs — filtered

The table exists, so is_incremental() returns true, the filter is compiled in, and only rows newer than the current maximum are processed.

3
Merged by key

unique_key tells the delete+insert strategy which existing rows to replace, so late updates to a known order overwrite instead of duplicate.

Mind late-arriving data and full refreshes

A strict > on max(order_date) misses rows that arrive later with the same or an earlier date. Many teams add a lookback window such as >= (select max(order_date) - interval '3 days' ...). Also remember dbt run --full-refresh ignores is_incremental() and rebuilds everything.

Setting the materialization for a model #

You can set it in three places. The model-level config() block wins, then the folder settings in dbt_project.yml.

dbt_project.yml yaml 
name: 'ecommerce'
version: '1.0.0'
profile: 'ecommerce'

models:
  ecommerce:
    staging:
      +materialized: view
    marts:
      +materialized: table
      fct_orders:
        +materialized: incremental

The + prefix is required for config keys in dbt_project.yml. Anything set here is a default; a {{ config(materialized='...') }} inside the model overrides it.

Cost vs freshness: the real trade-off #

Materializations are how you buy freshness with compute. Views are free to store but expensive to read; tables are expensive to build but cheap to read; incremental models pay only for the delta.

ConcernViewTableIncremental
Storage costNoneFull tableFull table
Build cost per runNoneFull recomputeDelta only
Read speedSlow for heavy SQLFastFast
FreshnessAlways liveAs of last runAs of last filter
ComplexityLowLowHigher — you own the filter
A practical rule of thumb

Start every staging model as a view. Promote a model to a table once dashboard queries get slow. Reach for incremental only when the model is genuinely large and the cost of a full rebuild hurts. Ephemeral is a packaging choice, not a performance one.

Choosing quickly #

Light and always current?

Use a view. No storage, no scheduling, no stale numbers.

Expensive but read often?

Use a table. Compute once per run, read cheaply all day.

Huge and always growing?

Use incremental — and write a filter that matches your data's arrival pattern.

Just organizing SQL?

Use ephemeral to break up a query without creating an object.

Key takeaways #

  • The materialization decides how dbt persists a model's SQL; the default is a view.
  • View stores no data (always fresh), table rebuilds fully (fast reads), incremental processes only the delta, ephemeral stores nothing at all.
  • dbt does not auto-add the incremental filter — you write {% if is_incremental() %} where ... {% endif %} yourself.
  • unique_key and incremental_strategy control how new rows are merged into the existing table.
  • Set materializations per model with config() or per folder in dbt_project.yml using the + prefix.
  • Choose by cost and freshness: views for freshness, tables for read speed, incremental for scale.
