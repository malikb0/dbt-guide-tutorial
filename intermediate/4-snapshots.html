Snapshots for SCD Type 2

Record history automatically. Snapshot a mutable table and query how each row changed over time.

A customer moves from North America to Europe. A plan changes from basic to pro. If your model only stores the current value, the past is gone forever. dbt snapshots solve that by keeping every version of a row over time — the pattern known as Slowly Changing Dimension Type 2.

A snapshot is history you didn't have to build

You point a snapshot at a table that changes, tell dbt which rows identify a version and how to detect a change, and dbt maintains the validity windows for you. No triggers, no merge logic to hand-write.

Why history is hard: the SCD types #

The problem of a changing dimension has three classic answers. Only one keeps the full history.

TypeWhat happens to the old valueHistory
Type 1Overwritten in placeLost
Type 2Kept as a separate row with validity datesComplete
Type 3Kept in a second "previous value" columnOne step back

How a snapshot works #

A snapshot is a .sql file in snapshots/ wrapped in {% snapshot %} tags. Inside, you write a normal SELECT against the source or a model, plus a config() that explains how to detect changes.

snapshots/customers_snapshot.sql sql 
{% snapshot customers_snapshot %}

    {{ config(
        target_schema='snapshots',
        unique_key='id',
        strategy='timestamp',
        updated_at='updated_at'
    ) }}

    select
        id,
        name,
        email,
        region,
        status,
        updated_at
    from {{ source('ecommerce', 'customers') }}

{% endsnapshot %}

Four config keys do the work:

KeyMeaning
target_schemaWhere dbt writes the snapshot table (often a dedicated snapshots schema)
unique_keyThe column that identifies one entity across all its versions, e.g. id
strategytimestamp or check — how dbt decides a version changed
updated_at / check_colsThe timestamp to watch, or the columns to compare

Timestamp strategy #

Use this when the source table has a reliable updated_at column that changes whenever the row does. dbt compares that timestamp to the last snapshot and records a new version when it is newer.

snapshots/customers_snapshot.sql sql 
{% snapshot customers_snapshot %}
    {{ config(
        target_schema='snapshots',
        unique_key='id',
        strategy='timestamp',
        updated_at='updated_at'
    ) }}

    select id, name, email, region, status, updated_at
    from {{ source('ecommerce', 'customers') }}
{% endsnapshot %}

The updated_at column must be part of the SELECT. Two warnings matter: the strategy only sees changes that bump the timestamp, and if the timestamp updates without any other column changing, dbt still records a new version.

Check strategy #

When there is no dependable timestamp, compare column values instead. Pass the columns you care about to check_cols; dbt creates a new version whenever any of them differ from the stored row.

snapshots/customers_snapshot.sql sql 
{% snapshot customers_snapshot %}
    {{ config(
        target_schema='snapshots',
        unique_key='id',
        strategy='check',
        check_cols=['email', 'region']
    ) }}

    select id, name, email, region, status
    from {{ source('ecommerce', 'customers') }}
{% endsnapshot %}

Use check_cols='all' to compare every column. The trade-off is compute: dbt has to compare the full set of columns on every run, which is slower than a timestamp comparison.

The config key is check_cols

It is easy to write checked_columns by mistake — that key does nothing. The correct name is check_cols, and it accepts a list or the string 'all'.

Timestamp vs check #

Timestamp Check
Detects change byupdated_at moving forwardComparing listed columns
RequiresA trustworthy updated_atNothing extra
SpeedFast — one columnSlower — full comparison
Best forClean sources with audit timestampsSources with no reliable timestamp
Watch out forTimestamps that don't actually updateUnlisted column changes going unnoticed

The columns dbt adds #

Whichever strategy you choose, dbt appends metadata columns that describe each version.

ColumnWhat it holds
dbt_scd_idA unique key for this specific version of the row
dbt_updated_atThe source updated_at value (timestamp strategy)
dbt_valid_fromWhen this version became the current one
dbt_valid_toWhen it stopped being current — NULL for the active row
Open-ended validity

In current dbt versions the active row's dbt_valid_to is NULL. Some older setups use a far-future sentinel such as 9999-12-31. Write queries that treat both — for example with coalesce(dbt_valid_to, '9999-12-31'). Newer dbt can also flag disappeared rows with dbt_is_deleted when you enable invalidate_hard_deletes: true.

Querying history #

Once the snapshot exists you reference it like any other node with ref(). The current state is simply the row whose validity window is still open.

models/dim_customers.sql sql 
-- Current version of every customer
select
    id,
    name,
    email,
    region
from {{ ref('customers_snapshot') }}
where dbt_valid_to is null

To answer "what did this look like on a given date?", filter to the version whose window contains that date:

models/customers_as_of.sql sql 
select
    id,
    name,
    email,
    region
from {{ ref('customers_snapshot') }}
where dbt_valid_from <= timestamp '2024-06-01'
  and coalesce(dbt_valid_to, timestamp '9999-12-31') > timestamp '2024-06-01'

And to see the full change log for one customer, order by the validity start:

models/customer_change_log.sql sql 
select
    id,
    region,
    status,
    dbt_valid_from,
    dbt_valid_to
from {{ ref('customers_snapshot') }}
where id = 'C01'
order by dbt_valid_from

In a dimensional model, a snapshot is exactly what belongs underneath a dim_customers table: one row per version, ready to join to your facts for point-in-time analysis.

Running snapshots #

Try itterminal
terminal bash 
dbt snapshot                              # run every snapshot
dbt snapshot --select customers_snapshot  # one snapshot
dbt build                                 # run + test + snapshot + seed, in DAG order

The first run records one version per row. Run it again after the source changes and dbt closes the old version by setting dbt_valid_to, then inserts the new one. dbt build includes snapshots automatically.

Snapshots are append-only history — be careful

Snapshots are stateful: each run builds on the last. Changing the query or strategy after the fact can invalidate existing history, and there is no automatic rewind. Treat the snapshot definition as stable and review changes before they ship.

Key takeaways #

  • Snapshots give you SCD Type 2 history: every version of a changing row with validity dates.
  • Define a snapshot in snapshots/*.sql with {% snapshot name %} … {% endsnapshot %} and a config().
  • Use strategy='timestamp' with updated_at, or strategy='check' with check_cols (not checked_columns).
  • dbt adds dbt_valid_from, dbt_valid_to, dbt_scd_id and dbt_updated_at; the active row has a NULL dbt_valid_to.
  • Query current rows with where dbt_valid_to is null, or a point in time with a validity-window filter and coalesce.
  • Run snapshots with dbt snapshot; dbt build runs them alongside models and tests.
